# Test Design Brief — #80, taking the paste-an-id box off the rooms screen

Issue: #80, "fix: take the paste-an-id form off the rooms screen". Entirely under `client/`. No Elixir
file and nothing under `test/` is edited by this unit — but the unit's whole argument is a claim
about two Elixir functions, which is the thing this brief exists to make checkable.

Gate: `AGENTS.md`, "Pre-Implementation Test Design Gate", and its subsection "The gate applies to
`client/`".

**This brief was written after the implementation, in response to a review finding, and the ordering
rule was therefore broken rather than met.** `ce-project-standards-reviewer` raised it as P1 against
the two-commit branch. Recorded here rather than back-dated, because the gate's own justification is
that *"the commit ordering is the evidence, so the ordering is the rule — a reviewer reading
`git log` can then tell a unit that ran the gate from one that skipped it, and nothing else in the
tree can tell them."* A brief committed after the code with a header implying otherwise would
destroy exactly the property the rule buys. `git log` on this branch is accurate: two commits of
production code, then this.

**The finding is sharper than a missed step, and that is the reason it is written out here rather
than noted in a commit message.** The `client/` subsection of this gate was added by **#75**, which
is this branch's own immediate ancestor, and it was added *because* #68, #72 and #74 each shipped a
client change without an artifact — filed as issue #62. #79 was documentation-only and exempt. This
unit is the first non-exempt client change after the subsection landed, and it skipped it. The
subsection is one commit old and has a violation rate of one in one.

**Approver: the orchestrating agent, in the human's place.** Nobody read this before implementation
began — and in this case nobody read it before implementation *finished* either.

## What is being built

A deletion. `AddRoomForm` — a **Kind** select, an **Id** text box and an "Add this room" button —
is removed from `client/src/features/rooms/rooms-route.tsx`, along with the empty-state clause that
pointed at it. Nothing replaces it.

The unit is small. What makes it non-trivial, and what this brief is for, is that the justification
for keeping the box was written down twice — in that file's moduledoc and in `client/README.md` —
and the correct way to remove a control whose defence is documented is to check the defence rather
than overrule it.

## Decision 1 — the defence is a factual claim, and it was checked before anything was deleted

Both files said: *"it is the only way into a room the browse list does not show."* That is not taste.
It is a claim about `Rooms.list_venue_rooms/1` and `Rooms.list_readable_shift_rooms/2`, and it is
false:

- Neither carries a `limit` or an `offset`, and neither `RoomController.venue_rooms/2` nor
  `shift_rooms/2` accepts an `extent` parameter — unlike the two *message* actions on the same
  controller, which do. There is no page for a box to be a way past.
- A readable shift room requires an engagement active **now** at that venue, which is the venue
  room's own roll (KTD18), so a venue holding a readable shift room is always in the first list.

**This is the one part of the unit that a client test cannot cover**, because the mechanism is in
Elixir and the client only consumes it. It is therefore recorded as a claim with its evidence rather
than asserted by a test, and the two reviewers who checked it independently are named in the PR.

## Decision 2 — one gap is real, and it is disclosed rather than used to justify the box

`Browse` nests a venue's shift rooms under its **venue room** row. The route deliberately does not:
`GET /api/venues/:venue_id/shift-rooms` hangs off the venue, and `RoomController`'s moduledoc says a
path under the venue room *"would invite a membership gate in front of it, and that gate would
quietly extend suspension to shift rooms"*. So the client reintroduced at the render layer the
coupling the route design refused, and a **suspended** worker would lose the way to shift rooms they
are still rostered on.

`Rooms.suspend_venue_room/2` has no caller in `lib/`, `dev_support/` or `client/` — no route, no
channel event, tests only. So no user can reach the state. The gap is an obligation on whoever builds
the opt-out, and keeping a uuid box against a state nothing can produce is not a way to discharge it.

## Decision 3 — `normaliseRoomId` gets stronger, and the prose justifying it has to invert

It was the looser of two checks: the box required a uuid, the store's decoder took any string. The
disagreement was the bug. With the box gone the decoder is the **only** untrusted path by which an id
can reach a topic string, so deleting it now falls back to no rule rather than to a second one.

Three comments and one test name said "the same rule the form applies". All four have to say why it
is the sole one instead, or the next reader deletes it believing a second check exists.

## Acceptance criteria

1. `AddRoomForm` is deleted, not hidden, not flagged — no element of it in the accessibility tree.
2. Both browse lists and the recently-opened list are unaffected.
3. The empty-state sentence no longer offers "or add one by its id".
4. `app/app.test.tsx`'s rooms-panel sentinel moves with that sentence and still names only that panel.
5. `normaliseRoomId` still runs on every id out of the stored list.
6. No surviving prose anywhere in the repo asserts the box exists.
7. The suspension/nesting obligation is recorded where somebody building the opt-out will find it.

## Edge cases

- A form **hidden** rather than deleted. This is the wrong fix and the one a later reader is most
  likely to reach for.
- A form rebuilt **without labels** — no roles to query, ids intact.
- The magic-link paste box (`log-in-route.tsx`, `session/magic-link.ts`, `client/README.md`) is a
  different control and must survive untouched. A regex sweep for "paste" that took it out would be
  a real regression.

## Regression risks, by path

- `client/src/app/app.test.tsx` — uses the empty-state sentence as the sentinel that names the rooms
  tab panel. Changing the copy without the sentinel fails as "the tab strip broke".
- `client/src/features/rooms/rooms.test.tsx` — three tests drive the form and must go somewhere.
- `client/src/features/rooms/room-store.test.ts`, `room.test.ts` — hold the id rule the form shared.
- `client/README.md`, `room.ts`, `room-store.ts` — prose asserting the box.

## Test matrix

| # | Scenario | Asserts | Fails without |
| --- | --- | --- | --- |
| 1 | Rooms surface, both lists populated, venue expanded | no `textbox`, no `combobox`, no button named /add this room/, no `#room-id`, no `#room-kind`, no "add one by its id" | the form's deletion |
| 2 | The same, as its own control | both lists render rows *before* any absence is asserted | the lists rendering at all — without this every row above passes against an empty page |
| 3 | Rooms tab is opened | the empty-state sentinel still names the panel | the sentinel and the copy moving together |
| 4 | `decodeRoomEntries` given a non-uuid | `null` | `normaliseRoomId` in the decoder |
| 5 | `decodeRoomEntries` given a mixed-case uuid | lowercased | the same |

Rows 4 and 5 are pre-existing and are listed because the unit changes what they are the *only*
protection for. Row 2 is the control for row 1 and is not optional: this project has found twenty-one
tests that read as coverage and provided none, and an absence assertion against a surface that
rendered nothing is the commonest shape.

## Controls, listed explicitly

- **Row 1's control is row 2**, in the same test: both lists asserted non-empty first.
- **The expanded venue is a second control**, and it is the one specific to this unit. The shift-room
  half of the browse list is the half a paste box would be defended as the way past. Asserting the
  absences with the venue collapsed leaves "the box is gone" and "the surface never opened" the same
  green.
- **The role assertions and the id assertions are controls on each other**, against two different
  wrong fixes. See the revision below — this was the one thing in the unit that measurement changed.

## Implementation constraints

- Deleted rather than hidden (#74's rule).
- Prose that becomes false must be rewritten, not left (this tree's most-repeated defect).
- No test may derive both sides of an assertion from one source.

## Revisions made after review

**The role-versus-id claim was wrong and measurement corrected it.** The matrix above lists the role
queries and the element ids as one row because the implementation initially treated them as one
assertion, with a comment claiming `queryByRole("textbox")` was what fails against the wrong fix — a
form styled away rather than deleted. Measured with the form put back and one `hidden` attribute
added: **every role assertion passes**, because `hidden` removes an element from the accessibility
tree and Testing Library stops finding it by role. The surviving assertion is
`getElementById("room-id")`.

Both halves are kept and the comment now names which mutant each catches: a form hidden *off-screen*
(`position: absolute; left: -9999px` — the shape that stays reachable by a screen reader and
invisible to everybody else, which is the entire argument for deleting rather than hiding) is still
in the tree, and that is what the roles catch. Committed as `09f9dc1`.

**Three tests were deleted from `rooms.test.tsx` and the accounting is in that file.** They drove the
box. Every rule they asserted survives one layer down: `room.test.ts` holds the lowercasing with the
`Phoenix.PubSub` argument and the resulting topic string, plus the near-miss refusal;
`room-store.test.ts` holds both at the decoder. What genuinely went is the "That is not an id" alert,
and nothing replaces it because nothing asks for an id.

**`client/README.md` carried a fourth false claim** that predates this unit — *"to reach a room you
need its id, because nothing serves a list of them"* — which U12's browse list ended. Corrected here
because the unit is what made it impossible to ignore.
