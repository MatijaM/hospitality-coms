# Test Design Brief — #65, what the speaker does at this venue

Issue: #65, "feat: attribute chat messages by role label, not a bare uuid". Sibling of #66, which
shipped first and answered the half of #65 that was about *who* spoke.
Gate: `AGENTS.md`, "Pre-Implementation Test Design Gate". Written and committed before any
production code, so the ordering is visible in the history rather than asserted. Convention
established by `docs/test-designs/2026-07-27-u5-engagement-lifecycle.md` onward, including the
"record revisions rather than applying them silently" section at the end.

**Approver: the orchestrating agent, in the human's place.** Nobody read this before implementation
began. Recorded here because `AGENTS.md` requires the substitution to be visible in the artifact
rather than inferred from the absence of a review.

## What is being built, and why the issue's own motivation no longer applies

The issue opens with *"a chat where you cannot tell who spoke is not a chat"*. **That sentence is
false as of #66**, which put `author_display_name` on every rendered message: a venue room now reads
`Captain Nemo · 4a3f1b2c`. Repeating it would be documenting a state the tree left three days ago.

What is still missing is different information, and it is the operationally useful half. A name says
*who*; a role label says **what that person does at this venue**. "The Manager said this" and "a
Bartender said this" are not the same message, and in a work chat the second one is often the part
that decides whether you act on it. `role_label` is employer-authored and venue-local — the same
column an invitation set and an engagement carries — so it answers that question in the venue's own
words rather than in the speaker's.

So: `author_role_label` beside `author_display_name` on `HospitalityComsWeb.RoomChannel.rendered/1`,
both room kinds, both transports, and the client renders `Name · Role · id`.

## Decision 1 — server-side, and the cost the issue hedged on does not exist

The issue weighs a client-side join against the venue room's roll versus a server-side field, leans
server-side for the ended-engagement case, and hedges: *"costs a join in
`Records.venue_room_messages/2`"*.

**Verified against the tree: there is no join to add.** `Rooms.Records.with_author_display_name/1`
(`lib/hospitality_coms/rooms/records.ex:768`) already joins `room_messages → engagements → people`,
and `role_label` is a column on `engagements` — the *first* of those two joins, already bound in
that query as `engagement`. So this is one more entry in an existing `select_merge` against a table
already in the FROM list. The plan estimate the decision was hedged on is zero.

Everything else the issue says for the server side stands and is now decided rather than leaned on:

- A venue room keeps **full history** (R14, KTD14) while `Rooms.list_venue_room_members/2` is the
  venue's **active** engagements, so a client-side join has nothing to find for a message whose
  author's term has closed. That case is ordinary, not rare.
- The same join serves a shift room, so the server does it once where a client would do it twice.
- Since #66 the field arrives at exactly four call sites — `Rooms.page/2` for both extents and
  `Rooms.naming/1` for both sends — all of which already compose the one function. One line changes
  and four paths move.

## Decision 2 — the function is renamed to `with_author/1`

After this change `with_author_display_name/1` merges two fields and one of them is not a display
name. A function whose name enumerates one of the two things it does is a name that will be wrong
again the next time somebody adds a third, and the tree's own rule for this is
`VisibleCorrection`'s: one shape, one spelling, and the spelling describes the shape.

`with_author/1`. Every reference moves with it: three call sites in `rooms.ex`, `Records.message/1`'s
docstring, `RoomMessage`'s moduledoc, `RoomChannel`'s moduledoc, `client/src/features/rooms/decode.ts`'s
docstring, and one comment in `rooms_test.exs`. It is a rename with no behavioural content, so it
carries no test of its own — a stale reference is a compile error for the call sites and a `grep`
for the prose.

## Decision 3 — an erased author renders **both** constants, and the doubling is named out loud

Erasure overwrites two things this render carries, with two separate constants:
`Lifecycle.erased_display_name/0` is `"Former colleague"` on `people.display_name`, and
`Lifecycle.erased_label/0` is `"Former team member"` on `engagements.role_label`. So an erased
author's message renders:

> **Former colleague · Former team member · 4a3f1b2c**

which reads oddly and is correct. Three things say leave it:

1. **They are two different facts.** One is what a person called themselves; the other is what an
   employer wrote about a job. #66 recorded them as deliberately separate constants with **no
   asserted relation** precisely so that neither could quietly become the other.
2. **Suppressing one would be the only special case in a render function that has none.**
   `rendered/1` is five field reads and a guard. A branch on "is this the erased name" would put a
   `Lifecycle` dependency into a channel render and a UI decision into a shape three surfaces share.
3. **The alternative is worse in the direction that matters.** Rendering only the label loses "this
   person is gone"; rendering only the name loses "this was a manager speaking", which is the whole
   of this issue. Collapsing them into one string is a client rendering choice the client can make
   later without a server change.

Recorded in `RoomChannel.rendered/1`'s moduledoc with the doubling written out, so a reader who
meets it in a demo finds it described rather than discovers it.

## Decision 4 — the id stays, for the same reason #66 kept it

Two people can hold the same `role_label` at one venue — "Bartender · 4444…" and "Bartender · 8888…"
— exactly as two can be given the same display name. Neither field disambiguates, both together
still do not (a venue can have two Captain Nemos who are both bartenders), and
`author_engagement_id` is the only value on the wire that does. It is also venue-local by
construction (KTD15b), which the other two are not: `display_name` is global, and `role_label` is
venue-local but not unique.

So the render is three values and the client shows all three.

## Decision 5 — the send reads the label back through the join, and this is a **shape** decision rather than a correctness one

⚠️ **This is where this unit departs from its own brief-in-advance, and the departure is a finding.**

The orchestrating brief warned that #66's trap is open here: *"an `EmployerScope` or a resolved
engagement in hand at send time is exactly the tempting shortcut"*, citing #66's measurement of
**13 kills** for taking the display name off the scope.

**It is not the same trap, and the difference is checkable.** #66's failure was that
`HospitalityComsWeb.ChannelAuth.person_scope/1` builds `%Person{id: person_id}` and nothing else, so
`scope.person.display_name` is `nil` on both channels and correct over HTTP. That asymmetry does not
exist for the label: both sends resolve a **whole `Engagement` row out of the database** before they
insert —

- `Rooms.fetch_membership/2` → `Records.venue_room_membership/3` → a full `Engagement`;
- `Rooms.fetch_shift_room_member/2` → `Records.shift_room_members/2` → a full `Engagement`;

— and both run inside the same transaction as the insert, with no writer able to touch
`engagements.role_label` in between. So `engagement.role_label` at send time is the *same string*
the join would return, on both transports.

**The label is read back through the join anyway**, and the honest reason is that it costs nothing
and buys one spelling. `naming/1` already issues that query for the display name; the `select_merge`
fills both virtual fields in the same row. Taking one field from the query and the other from a
struct in hand would put two sources behind one rendered shape, which is the defect class this tree
has fixed four times.

**Predicted kill count for the corresponding mutation: 0.** It is written into the matrix as 0
rather than discovered afterwards, because a brief that predicts a kill and gets a zero is how the
last twenty-five vacuous tests were found. What holds the read-back in place is #66's M5 at 13, on
the field beside it, and that is stated rather than borrowed silently.

## Decision 6 — one new disclosure, small and on the record

`role_label` reaches no new *employer*: `room_messages` is read person-side only, `employer_role`
holds nothing on that table, and the label is employer-authored in the first place.

Worker-to-worker it is almost entirely already-disclosed. `Rooms.list_venue_room_members/2` hands
every member the whole `Engagement` struct of every other member, label included, and
`Peers.list_visible_peers/1` carries a counterpart's label by design. **One case is genuinely new**,
and it follows from exactly the property this unit turns on:

> The roll is the venue's **active** engagements and peer visibility lapses thirty days past an
> engagement's end. A venue room keeps full history. So after this change, a worker who joined a
> venue last week can read from the room's history that somebody who left two years ago was the
> **Head Chef** — which neither the roll nor the peer list would have told them.

It is a job title at a venue, authored by that venue, attached to words that venue already retains
indefinitely under KTD15c. Recorded in `CLAUDE.md`'s "Five disclosures on the record" rather than
closed, because closing it means either dropping history's attribution or storing a snapshot label
on `room_messages`, and the second is KTD2 broken for the same reason a stored display name is.

## Acceptance criteria

1. `RoomChannel.rendered/1` carries `author_role_label` on the channel reply, the channel broadcast
   and the HTTP history, for both room kinds, with one key set.
2. `rendered/1` heads on the label being a binary, so a read path that forgot the join crashes here
   rather than putting `null` on the wire.
3. A message whose author's engagement has **ended** still carries the label.
4. A message whose author has been **erased** carries `Lifecycle.erased_label/0`, beside
   `Lifecycle.erased_display_name/0`, and the two are different strings.
5. The label is the author's at **that venue** — a person engaged at two venues under two labels is
   rendered differently in the two rooms.
6. `author_engagement_id` is still on the wire beside both new fields.
7. `Records.with_author_display_name/1` is `Records.with_author/1`, with no reference left behind.
8. The client renders `Name · Role · id` in both room kinds, and still "You" for its own messages.
9. `decodeRoomMessage` requires `author_role_label` and refuses a payload without one.
10. No employer surface gains the field; the person-zone sweep is unchanged and still green.

## Edge cases

- A label at the CHECK's bound. `engagements.role_label` is `NOT NULL` with
  `length(btrim(role_label)) > 0` and `length(role_label) <= 160`, so it is always a non-empty
  string. Nothing new is written here, so this unit adds no constraint and no
  `constant_agreement_test.exs` row — but the guarantee is what makes `is_binary/1` the right head.
- An erased author whose *label* was reduced and whose *name* was not, or the reverse. Not reachable:
  `Lifecycle.erase_person/1` does both in one transaction. Asserted as one state rather than two.
- Two authors with the same label in one room — the id is the disambiguator, and that is the same
  control #66 wrote for the same reason on the field beside it.
- A shift-room message. Same table, same join, same render; the risk is a change applied to one read
  path and not the other, which is what `Rooms.page/2` being the single place either extent becomes
  a query already prevents.
- A message read by a path that never composes the join — `lifecycle_test.exs:368` and
  `retention_sweeper_test.exs:590` both hold `%RoomMessage{}` structs straight out of `Repo`, where
  both virtual fields are `nil`. Those must keep working: they never reach `rendered/1`.

## Controls, listed explicitly

- **Row 2 controls row 1, and it is the row that says what "venue-local" means.** A label resolved
  through `people` rather than through the message's own `author_engagement_id` satisfies row 1
  completely for every single-venue fixture in the file — which is every fixture in the file. The
  mutation is written out in the table below and its kill count is reported whatever it turns out
  to be.
- **Row 3 controls row 1 in the other direction, and it is what Decision 1 turns on.** An activeness
  predicate on the join satisfies rows 1, 2, 5 and 7 and produces `nil` for exactly the messages a
  venue room keeps history for. #66 measured that mutation at 3 kills on the field beside this one;
  the expectation is that it roughly doubles.
- **Row 4 is two assertions and needs to stay two.** `assert label == erased_label()` alone passes
  if a render collapsed the two constants into one, so `refute erased_label() == erased_display_name()`
  is beside it — the same pin `lifecycle_test.exs:244` already carries, restated where the doubling
  is visible.
- **Row 6 controls Decision 4.** Dropping the id from the render satisfies rows 1–5 and 7–10.
- **Rows 7, 9 and 10 are exact key sets**, which are the only assertions that fail when a field is
  *added* — the direction `person_id` arrives from. Row 10 is a control in a different shape from
  row 9 rather than a copy of it: it compares the shift room's key set against the venue room's, so
  a divergence fails even if both files' literals were updated together.
- **Row 11 is the guard's own test and it will be reported honestly.** #66 claims `is_binary(name)`
  "turned a `null` on the wire into a crash the suite could see". The mutation that checks this is
  "drop the guard, drop the join" — dropping the guard alone changes nothing observable, and if that
  is what the measurement says, it is recorded as a **redundant pair, measured**, in the tree's
  existing sense (`EmployerController`'s `@term_fields`, `Rosters.unrostered/3`).
- **Row 14 controls row 13.** A client that labelled every message would satisfy row 13.
- **The absence assertions in this unit are `refute Map.has_key?(message, "person_id")` and the
  exact key sets that already carry them.** Both are inherited unchanged and both already have their
  control: the key set is asserted against a written-down literal, not against the other side of the
  comparison, and the message list is asserted non-empty by pattern-matching one element out of it.

## Implementation constraints

- **No new column.** `author_role_label` is virtual on `RoomMessage`, like `author_display_name`. A
  stored label is a denormalised copy an employer's correction never reaches, and — since erasure
  overwrites `engagements.role_label` — it would make erasure an unbounded write proportional to
  messages, which is the exact thing KTD15b put the label on the engagement to avoid. **No migration
  in this unit**, and `boundary_test.exs`'s column lists staying untouched is what proves it.
- **The clock rule.** No new `Clock.now/0` caller and `.credo.exs`'s `:boundary_modules` does not
  grow. Nothing here reads an instant.
- **`@spec` on every public function, with enumerated error atoms.** `rendered/1`'s `@type rendered()`
  gains the field; it is the contract the client is written against.
- **Queries live in `Records`.** The `select_merge` is `Rooms.Records`' and nothing in `Rooms` gains
  a query builder.
- **`RoomChannel.rendered/1` is the single spelling of a message.** The change happens there and
  nowhere else; `RoomController.render_message/1` keeps delegating.
- **Never migrate `hospitality_coms_dev`.**
- Gates: `mix format --check-formatted`, `mix compile --warnings-as-errors`, `mix quality`,
  `mix test`. Baseline **1241/1245**, the four `PostgresRolesTest` failures being issue #20's
  documented `hospitality_coms_dev` condition. Client: `npm run verify`, baseline **511 passed / 15
  skipped**.
