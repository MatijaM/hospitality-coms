## CI, and the test database it must not share

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main`, in two parallel jobs. Before it existed, **every green suite in this project's history was one machine's local run.**

- **Elixir** — `mix deps.unlock --check-unused`, `mix format --check-formatted`, `mix compile --warnings-as-errors` under `MIX_ENV=test`, `mix test`, then `mix quality`. Versions come from `.tool-versions` through `erlef/setup-beam`'s `version-file`, which is the only place they are written; that input requires `version-type: strict` and the action errors without it. `deps/` and `_build/` are cached on `mix.lock` and the resolved OTP/Elixir versions, and `priv/plts/` is cached separately — without it every run pays several minutes rebuilding the Dialyzer PLT. The application's own build artefacts are deleted before compiling so `--warnings-as-errors` sees every file rather than the ones that push happened to touch; the dependency build stays cached, which is where the minutes are. `mix quality` runs in **dev**, not test, because `elixirc_paths(:test)` adds `test/support` and CI going red for something `mix quality` on a developer's machine cannot reproduce is worse than the coverage is worth.
- **Client** — `npm ci` then `npm run verify` (typecheck, lint, format check, vitest, build). Three integration files skip themselves when no server answers; that is correct and CI does not stand one up.

Two hazards, both specific to this repository:

- **The service container is `postgres:17` and connects as the image's default superuser, and both halves are load-bearing.** `Zones.employer_privileges/1` asks `has_table_privilege` about `MAINTAIN`, which does not exist before 17 — on 16 the sweep raises rather than answering. And `boundary_test.exs` asserts `rolsuper` is true for `current_user`, because KTD3's argument is that a superuser bypasses row-level security whether or not a policy is `FORCE`d. "Hardening" CI onto a non-superuser fails around twenty-five tests in ways that read as unrelated to the change under review.
- **Never `mix test --partitions`.** `config/test.exs` interpolates `MIX_TEST_PARTITION` into the database name, so a partitioned run creates a second and third database on the same cluster, each of which runs the grant migrations. Grants are database-local while roles are not, so `PostgresRolesTest`'s `DROP ROLE` then fails, naming the partition databases. A reviewer hit exactly this. One service container per job is a fresh cluster holding one database, which is what keeps that closed; the suite is well under a minute and partitioning buys nothing worth the failure mode.

The same cluster rule applies locally, and it is not theoretical: **two checkouts running `mix test` against one Postgres cannot both be right.** They share `hospitality_coms_test`, so one worktree's `ecto.migrate` puts the other's schema ahead of its own migrations, and the non-sandboxed fixtures' `purge/0` deletes any `u5-venue%` row including the other run's. Give a second checkout its own cluster (a throwaway `initdb` on another port), not its own database on the shared one.

## The test-database guard

`HospitalityComs.TestDatabaseGuard.sweep/0` runs once from `test_helper.exs`, before the sandbox goes to `:manual` and therefore before any test. On a database that is already empty it issues one query and prints nothing.

**What it is for.** Ten test files are not sandboxed and commit for real. A run that dies between the purge that opens a test and the one that closes it leaves rows behind, and the result is roughly 150 errors across nineteen modules that read exactly like a regression in whatever was last committed — measured at 371 failures across 20 modules on this branch, twice in a row, from one leftover engagement plus two hand-typed rows. Two reviewers lost significant time to it before bisecting to a `DELETE`.

**It does not reliably heal by itself, and where it does, it is by accident.** `purge/0` is one transaction: a row it does not know about that references a row it does delete makes the whole thing raise `foreign_key_violation` and roll back, so the next run fails identically. `oban_jobs` is keyed on venues the purge can still find, so a job outliving its venue is unreachable for ever. What *does* clean up on this branch does so incidentally — `engagement_sweeper_test.exs` deletes every `oban_jobs` row for its worker and `accounts_concurrency_test.exs` deletes every person at `example.com` — which is worth knowing but is not a mechanism anybody designed.

**It cleans rather than refusing, and reports what it cleaned.** The correct contents before the first test are empty: nothing seeds this database and no fixture is meant to outlive its test, so there is nothing to weigh up and refusing would make everybody paste the same `DELETE`. What is worth weighing up is silence, which would hide a real leak behind a suite that goes green anyway — so it prints a banner to stderr and splits the residue three ways rather than reporting one number: what the fixtures' own purge removed, what survived it in `oban_jobs`, and what survived it anywhere else. The third is the loud one; it is where a hand-typed `psql` row lands, and where everything lands when the purge raised before reaching it.

**Two implementation facts that are not incidental.** The table list comes from `pg_class` rather than from `Zones`, because a table created by a migration with no schema module holds rows just the same and a branch switch leaves this database carrying tables the checkout has never heard of. And the fallback for what the purge cannot reach is one `TRUNCATE ... CASCADE` over every table at once — one statement, so there is no foreign-key order to get wrong and nothing to deadlock against — with identifiers quoted by Postgres's own `format('%I')`. Do not replace the purge with a second hand-written ordering; reuse is what keeps the `ON DELETE RESTRICT` chain through `employer_grants` in one place.

`test_database_guard_test.exs` reproduces each of the three residues and the raising purge. It is `async: false` and non-sandboxed, which is what makes its `TRUNCATE` legitimate: ExUnit finishes every async module before starting a synchronous one, so the only committed rows while it runs are its own.

## Time

`HospitalityComs.Clock` is the only source of the current instant. `HospitalityComs.Credo.Check.ClockAuthority` enforces it:

- `DateTime.utc_now/*` is flagged anywhere outside the `HospitalityComs.Clock` namespace.
- `Clock.now/0` is flagged outside the modules listed in the check's `:boundary_modules` parameter in `.credo.exs`. That list holds seven entries: `HospitalityComsWeb.PersonAuth` (the HTTP boundary), the four Oban workers `Workers.ExpireEngagement`, `Workers.EngagementSweeper`, `Workers.RetentionSweeper` and `Workers.AccountReaper` — one job attempt is one unit of work, and a retry is a new one that correctly reads the clock again — `HospitalityComsWeb.ChannelAuth`, the channel boundary U7 added, and `HospitalityComs.Demo`, U11's: one seed run, one `run_due_work/0` pass, one `end_all_engagements/1` is each one unit of work. `HospitalityComsWeb.DemoController` is deliberately **not** on the list and reads no clock, so a request and the control it invokes cannot disagree about when they are; nor is `HospitalityComsWeb.LoginRateLimit`, which is a plug behind `fetch_person_scope` and derives its window from the instant already on the scope. When you build another, add it there rather than working around the check.

  `ChannelAuth` is deliberately **one** entry for the seven modules that would otherwise need one: two sockets, four channels, and `RoomChannel`, which the two room channels share. Naming them all would turn the allowlist into an inventory of whatever happens to call the clock. Everything on the transport takes its instant from a scope `ChannelAuth` built.

Everywhere else, the instant arrives on the scope struct — `%HospitalityComs.Accounts.PersonScope{person: _, now: _}`, assigned as `:current_scope` by `PersonAuth.fetch_person_scope/2`, or `%HospitalityComs.Accounts.EmployerScope{venue_id: _, now: _}`. `EmployerRepo`'s transaction wrapper takes the instant off the scope for the same reason; a repo is not a unit of work, so it is not a boundary module.

`Ecto.Query.ago/2` and `from_now/2` are banned for the same reason `DateTime.utc_now/0` is: they expand to `DateTime.utc_now()` inside the query macro, where the offsettable clock cannot move them. `ClockAuthority` flags the call itself, both imported and fully qualified, because by expansion time it is too late to see. Compare against an instant taken from the scope.

`HospitalityComs.Accounts.Person` stamps `inserted_at`/`updated_at` explicitly too — Ecto's `timestamps()` autogenerate reads the wall clock from inside Ecto, which is also out of the check's reach.

## Database

Two repos, one database.

- `HospitalityComs.Repo` — the application's own role. The only repo in `:ecto_repos`, so migrations run through it alone.
- `HospitalityComs.EmployerRepo` — logs in as `employer_login` and assumes the Postgres role `employer_role` via `after_connect`. Every read goes through `EmployerRepo.scoped_transaction/2`, which writes `app.employer_id` and `app.now` transaction-locally; an operation outside it raises `EmployerRepo.UnscopedError`, and a query reaching a person-zone table raises `EmployerRepo.ZoneViolationError` before Postgres is asked. Opening the wrapper again inside itself for a *different* employer raises `EmployerRepo.NestedScopeError`: there is no savepoint between the two, so the inner `set_config` would stay in force after the inner call returned. An identical scope nests freely and writes nothing.

PostgreSQL 17 is the minimum. `Zones.employer_privileges/1` asks about `MAINTAIN`, which does not exist before 17.

Neither guard is the boundary. **The boundary is now genuinely below them, which it was not before #17.** Two escapes remain, each pinned by a test in `boundary_test.exs` rather than only described:

- Raw `EmployerRepo.query/3`, `query!/3`, `query_many/3` and `to_sql/3` go to `Ecto.Adapters.SQL` without `default_options/1`, so the unscoped guard never sees them. That exemption is load-bearing — `write_settings/1` is a raw query issued before the scope is registered — so it is documented, not closed.
- A raw statement is not an `Ecto.Query`, so the zone guard never sees it either. Postgres refuses it.

There was a third, and it was the one that mattered: `RESET ROLE` returned the connection to a login role that owned every table, so the grant tier was defeatable from the same code position as the two guards above it and the boundary had one tier rather than three. #17 closed it. **The test that pinned it is inverted rather than deleted** — it asserted a defect the project had decided to record rather than hide, so leaving it would assert the bug back into existence; the replacement carries three controls where the original had one.

`employer_role` and `person_role` are created by `priv/repo/migrations/*_create_postgres_roles.exs`, and `employer_login` by `*_create_employer_login_role.exs`. Roles are cluster-global, not database-local; a test that drops one must run inside the sandbox transaction so it rolls back.

**`employer_login` is a credential and nothing else**, and three properties are what make it one. It is `NOINHERIT`, so `RESET ROLE` lands on a role holding *less* than `employer_role` rather than the same — under `INHERIT` the escape would be neutral instead of costly, and "after `RESET ROLE`, `venues` is denied" is the assertion that fails if somebody changes it. It is a member of `employer_role` and of no other role. And it is granted **no object privilege at all**, including `CONNECT` and schema `USAGE`, which it holds through `PUBLIC`: a grant of its own would write a `pg_shdepend` row and make `DROP ROLE employer_login` fail from every other database on the cluster. Measured: `GRANT employer_role TO employer_login` writes no such row, because membership lives in `pg_auth_members`.

`person_role` deliberately gets no login role. Nothing assumes it — `Repo` connects as the application's own role and there is no `SET ROLE person_role` anywhere in the tree — so a credential for it would be a live authenticating credential for a role no code path uses. Pinned as a test, with `employer_login` as the control.

**A migration may create a role and grant it membership; it may not mint a secret.** `*_create_employer_login_role.exs` writes a password only when the role does not already exist, and reads it from `EmployerRepo.config/0` — the one place that cannot disagree with what the application connects with, whichever way the environment spells it. So dev, test and CI bootstrap from a literal that sits beside the `postgres`/`postgres` already in those files, while production pre-provisions the role and the secret never reaches a migration, and therefore never reaches the Postgres statement log. `LOGIN` and `NOINHERIT` are re-applied on every `up` either way, because those are not secrets and a pre-provisioned role that got them wrong should be corrected rather than trusted.

Production requires `EMPLOYER_DATABASE_URL`, a *second* URL rather than a password beside `DATABASE_URL`. The reason is mechanical: `Ecto.Repo.Supervisor.init_config/4` merges the parsed URL **over** explicit options, so `username: "employer_login"` written next to the shared URL would be silently overwritten by that URL's own userinfo and the repo would go on connecting as the owner with nothing to say so.

**U1's two caps are real now, and until #45 they never were.** `ALTER ROLE employer_role SET statement_timeout = '5s'` and `idle_in_transaction_session_timeout = '10s'` — described in that migration as part of the time model — took effect on nothing for twelve units. Role-level settings are applied at login for the *session user* and `SET ROLE` re-reads none of them, so a connection that reached `employer_role` by assumption reported `statement_timeout = 0` with both rows sitting in `pg_roles`. #17 is what made the fix available: `*_bound_employer_login_connections.exs` puts the same pair on `employer_login`, the role `EmployerRepo` actually logs in as, and a live connection now reports `5s` and `10s` after `after_connect`.

**The numbers did not move, and that is a measurement rather than a default.** On a clean cluster with `log_min_duration_statement = 0`, the longest statement on an `employer_login` connection across the whole suite is **154 ms** — a `SELECT … FOR UPDATE` the concurrency files park on a lock deliberately, so it is the longest by construction — and the longest stretch such a connection spends idle inside a transaction is **1.2 s**, sampled from `pg_stat_activity`. The four files that park real connections on real locks were run five consecutive times each with the caps live: twenty runs, no failures, no `57014` and no `25P03` anywhere in the Postgres log. #45 asks specifically whether the retention sweep and the demo's `run_due_work/0` need more room; **neither is bounded by this at all, because neither touches `EmployerRepo`** — `Lifecycle` runs as the application's own role by design and `employer_role` holds no `DELETE` anywhere.

**`employer_role` keeps U1's inert copy on purpose.** It costs nothing and it stops being inert the day somebody gives that role `LOGIN`. What changed is the claim: `postgres_roles_test.exs` asserts it as a catalogue entry and says that is all it is, while `boundary_test.exs` asserts the behavioural half against a **live connection** — `current_setting/1` after `after_connect`, never `pg_roles`. That distinction is the whole of #45, and the control is what carries it: the same helper is pointed at a connection that reached `employer_role` by `SET ROLE`, where the catalogue says `5s` and the connection says `0`. Measured — a helper rewritten to read `pg_roles` leaves both live assertions passing and fails only that control.

**`Repo` still has no timeout of any kind, and #45 leaves it that way deliberately.** It connects as a superuser, and the naive fix is refuted by measurement: a role-level `statement_timeout` binds every new connection of that role including a superuser's, and `Repo` is what the migrator and the seeds run as — `add_retention_columns.exs` does a full backfill, a `SET NOT NULL` and two index builds against `room_messages`, which is exactly the statement a 5s cap kills halfway on a populated database. The tree already works around the absence in three places: `engagements_fixtures.ex`, `accounts_concurrency_test.exs` and `venues_concurrency_test.exs` each issue `SET LOCAL statement_timeout = '10s'` around their purge, because cleanup can block on rows another run holds. That `SET LOCAL` is the shape a real answer takes — a bound at the boundary that opens a unit of work, the way `EmployerRepo.scoped_transaction/2` already writes `app.now` — not an `ALTER ROLE` that cannot tell a request from a migration.

Grants are database-local while roles are not, so one privilege granted to `employer_role` in *any* database on the cluster makes `DROP ROLE employer_role` fail in every other — including the rollback `PostgresRolesTest` asserts on. `*_grant_zones.exs` deliberately creates no such dependency; `*_grant_employer_zone.exs` does, because the employer zone cannot be read without one.

**Issue #20 asked whether a `down` migration should drop cluster-global roles at all, and the answer is yes — it is closed as wontfix.** Its own text said option 3 was "fine for a POC with one developer and two databases on one cluster; bad the moment CI runs parallel test databases". CI now exists, gets one fresh service container per job holding exactly one database, and `ci.yml` carries an explicit prohibition on `--partitions` with that reason written out — so the condition that was going to force a change does not arrive. The remaining exposure is one developer's two databases, and it is detected, named and actionable. Moving role creation out of the migration sequence would trade that for an undetected failure, and #17 makes the trade worse: `EmployerRepo` now *logs in* as a role, so a missing provisioning step is not "a grant is absent" but "the application cannot open a connection", surfacing as a pool crash loop at boot rather than as a named assertion. The group-role alternative was measured for #4 and moves the landmine.

**But #17 added one new obligation on the down path, and it is silent.** Measured: `DROP ROLE employer_role` does **not** fail while `employer_login` is a member of it — memberships write no `pg_shdepend` row and are removed without complaint — and re-applying U1's `up` does not restore the membership, because the role that comes back is a fresh one with no members. So a roles migration rolled back underneath a live login role leaves a credential that authenticates and can assume nothing. `create_employer_login_role` is therefore in `PostgresRolesTest`'s rollback list for a different reason from every other entry, and the property itself is pinned as its own test.

**Consequence, and it will bite you.** `PostgresRolesTest` rolls every grant migration — `grant_employer_zone`, `grant_engagement_zone`, `grant_room_zone`, `grant_peer_zone`, `grant_profile_zone`, `grant_retention_zone`, `create_employer_login_role`, `bound_employer_login_connections` — down before it rolls the roles migration down, which is the real order Ecto uses. The last entry is #45's and is there for #17's reason rather than a `pg_shdepend` one: `DROP ROLE` takes a `pg_db_role_setting` row with it as silently as it takes a membership, and the role a re-applied `up` brings back carries neither — so a login role dropped underneath it leaves a credential that is *unbounded* while the migration log records it as capped. Measured: listing it out of apply order makes three of that file's tests fail with `role "employer_login" does not exist`. Every unit that adds a grant migration adds an entry to that list, `grant_peer_zone` included even though it grants nothing: the rule is "every grant migration", and a list with a judgement call in it is a list somebody gets wrong later. `grant_profile_zone` is the first that grants on something other than a table, so `boundary_test.exs`'s expected-dependency list is built in two halves — `pg_describe_object` says `view x` rather than `table x`, and a check that assumed the prefix would pass while naming the wrong objects. That fixes *this* database only. If you run `mix ecto.migrate` against `hospitality_coms_dev` (or any other database on the same cluster), its grants make `DROP ROLE employer_role` fail in the test database too, and no connection to the test database can revoke them. `PostgresRolesTest` detects that case and names the offending databases; the fix is to roll the grant migrations back there, or drop the database.

Grant explicitly, per table, per privilege. `ALTER DEFAULT PRIVILEGES` is the one thing that must never be used: it survives `REVOKE ALL ON TABLE` and is inherited by every table created afterwards, so it would hand `employer_role` person-zone tables that do not exist yet. `boundary_test.exs` asserts `pg_default_acl` names no role at all, with a control that grants one and watches the check catch it.

**A bound declared in a module and again in a migration is checked, not commented** (issue #42). A migration must replay to the schema it produced, so its literal can neither be edited nor derived — which rules out both of the mechanisms the rest of the tree uses for a pair of numbers that must agree. `test/hospitality_coms/constant_agreement_test.exs` reads the CHECK back out of `pg_constraint` and compares it against the module constant claiming to describe it: the two label bounds, the claim code's fourteen-day horizon, three message-body bounds, #66's display-name bound, and `retained_message_copies` being at least as wide as `room_messages` — the one of those that is an *ordering*, because a retained copy is written with `insert_all` and a room bound raised past it would raise `Postgrex.Error` inside the retention transaction rather than returning a changeset error. **The file's own reader raises on a constraint name that matches nothing**; without that every assertion in it passes against `nil`, and each is a long string nobody re-reads. Add a row when you add a bound.

The three mechanisms, and the rule for picking one: an **equality between two `lib` values** is derived at compile time (`Engagement` and `DeclaredEntry` both read `Invitation.max_label_length/0`); an **ordering** keeps both numbers declared and adds a compile-time `raise` (`Lifecycle`'s ceiling against a full batch per trigger, `EngagementSweeper`'s lookback against the pruner, `Lifecycle`'s unconfirmed retention against every token validity); a pair with a **migration literal or a config value** on one side gets a test. What must never happen is a test deriving both sides of one assertion from one source — it then agrees with itself for any value, which is why `peers_test.exs` keeps its own `@tail_days 30` and pins it in one line rather than calling `Visibility.tail_days/0` at the nine places it uses it.

## Zones

`HospitalityComs.Zones` classifies every Ecto schema as person zone, employer zone, or shared, and `ZonesTest` fails on any schema in none of them. The shared zone has exactly one member and always will: `engagements`, the single bridge. U8's three peer tables are person zone and had no alternative — see **Peer graph** below. U10's two are person zone as well, and `retention_runs` is the one placement in the tree that is a judgement rather than a forced move: it holds no personal data at all, and it is person zone because a zone answers *which privileges may `employer_role` hold* rather than *whose data is this*. See **Data lifecycle**. Adding a table is not finished until it is classified. Table names derive from `__schema__(:source)`; do not write a second list. That is nil for an embedded schema, and `Zones.tables/1` raises on it rather than handing Postgres a NULL the privilege sweep would silently skip.

**U9 added a kind of relation the zones had never had, and neither totality check reaches it.** `Zones.employer_views/0` is a list of *names*, not schemas: `ZonesTest` quantifies over Ecto schemas and there is none behind a view, while `boundary_test.exs`'s `database_tables/0` asks for `relkind IN ('r','p','m')` and excludes plain views on purpose, because they hold no rows. So `boundary_test.exs` carries a third totality check, over `relkind = 'v'`, with a control. A view-backed Ecto schema was the alternative and is worse: it would be swept as though it stored rows and would then have to satisfy the employer zone's structural rules — a `venue_id` column and a unique `(id, venue_id)` index — which a view cannot have, so the rule would grow an exemption. What the classification means for a view is what it means for a table: `employer_role` may hold privilege on exactly these, and on the views it holds `SELECT` and nothing else.

The sweep asks `has_table_privilege` *and* `has_any_column_privilege`: a column grant is invisible to the first. `GRANT SELECT (email) ON people TO employer_role` must fail the suite, and so must `GRANT SELECT ON people TO employer_role`.

The boundary's proof suite is `test/hospitality_coms/boundary_test.exs`, with `boundary_lifetime_test.exs` holding the parts that cannot be asserted inside the sandbox — there, `EmployerRepo`'s transaction is a savepoint inside the test's own, so a `SET LOCAL` survives its commit and the production lifetime is not reproduced. Measured: with the wrapper writing session-level settings instead, the sandboxed file still passes everything and the non-sandboxed one fails.

`employer_role`'s lack of privilege on `people` is Postgres default-denying as much as it is the `REVOKE`. Every assertion in that suite that could pass for that reason carries a control that fails when it does; keep that property when extending it.

## Employer zone

`venues`, `employer_grants` and `shift_types` from `*_create_venues.exs`, reached only through `HospitalityComs.Venues`; `invitations` and `attested_entries` from `*_create_engagements.exs`, reached only through `HospitalityComs.Engagements`; `correction_requests` from `*_create_profiles.exs`, reached only through `HospitalityComs.Profiles`.

**No employer-zone table may name a person.** Not `person_id`, not `created_by`, not a foreign key to `people` under any name — `boundary_test.exs` asserts it against `pg_constraint`, and the employer zone being non-empty is what stopped that rule being vacuous. A person creates a venue and no row records which person: `engagements` is the single bridge and carries `grant_id` referencing `employer_grants (id, venue_id)`, so the association is made from the person's side. Arrows point *into* the employer zone, never out. `boundary_test.exs` now also asserts the positive form — `engagements` is the *only* table outside the person zone with a foreign key to `people`.

**Venue-to-venue tenancy has a database tier.** `*_enable_employer_zone_row_level_security.exs` and `*_enable_engagement_row_level_security.exs` put row-level security on all six tables — `venues`, `employer_grants`, `shift_types`, `invitations`, `attested_entries`, and the bridge itself, which is one of the six rather than an addition to them — with one policy each — `USING` and `WITH CHECK`, both on the row's venue equalling `app_current_employer_id()`. Before it, isolation rested entirely on `Venues` pinning `venue_id` by hand, and one `EmployerRepo.update_all(EmployerGrant, ...)` with no filter passed both guards, passed Postgres, and revoked every grant in the database.

It is deliberately **not** `FORCE`d. The tables are owned by the application's login role, so `Repo`, the migrator and the seeds bypass the policies while `employer_role` is bound by them; FORCE would bind the owner too, and the predicate raises wherever `app.employer_id` is unset. Policies are granted to `PUBLIC` rather than `TO employer_role`, so they write no `pg_shdepend` row. This is not KTD3 reversed — KTD3's view-not-RLS decision is about the per-row hidden-entry rule and stands.

**Consequence for rollbacks.** The policies depend on `app_current_employer_id()`, which `grant_zones` drops with `RESTRICT` on purpose. Rolling `grant_zones` back without rolling this migration back first now fails loudly with `dependent_objects_still_exist` — which is that `RESTRICT` doing its job, and `boundary_test.exs` both rolls in the right order and pins the wrong one.

Every employer-zone table other than `venues`, and `engagements` too, carries `venue_id` and a unique index on `(id, venue_id)`, both asserted structurally. The composite index looks redundant next to the primary key and is what makes a composite foreign key possible — without it a later table can only reference `id`, and a row at venue A can point at a row belonging to venue B. `employer_grants.granted_by_grant_id` already uses one; it is `MATCH SIMPLE` rather than `MATCH FULL` because the founding grant has no parent and `venue_id` is `NOT NULL`, so MATCH FULL would reject the one row every venue must have. The rule is **MATCH FULL unless a column of the key is nullable**, and `boundary_test.exs` asserts it in that derived form plus the inventory it quantifies over — a `MATCH SIMPLE` key is one whose id is optional (`employer_grants.granted_by_grant_id` and `revoked_by_grant_id`, `invitations.grant_id`, `engagements.grant_id`, `room_messages.shift_room_id`, `correction_requests.resolved_by_grant_id`), and everything else is `MATCH FULL`. Read the inventory in the test rather than a count here; writing it out is what found `revoked_by_grant_id`, which U4's own documentation does not mention.

`EmployerScope`'s tenancy field is `venue_id`, because that is what it holds: there is no `employers` table and an employer session is scoped to a venue. The Postgres session setting is still `app.employer_id` and the SQL function is still `app_current_employer_id()` — they are literal strings written by a committed migration, and renaming them would be a schema change bought for a nicety.

`EmployerScope` also gained `grant_id`. `for_employer/2` builds a scope with tenancy and no authority — enough for `EmployerRepo` and for U9's per-employer view — and `for_grant/3` builds one with both. Every `Venues` function *other than* `create_venue/2` heads on `grant_id` being a binary, so a grantless scope is refused by function clause, and the grant is then resolved against the database on every call: live at the scope's instant, and belonging to the scope's venue. Nothing caches it. `create_venue/2` is the exception, and heads on a `PersonScope`: the grant it acts under does not exist until it writes it.

`Venues.revoke_grant/2` refuses the venue's last live grant (KTD17, R22) and takes the venue's live grants under `FOR UPDATE`, ordered by `(granted_at, id)`, before counting — the acting grant is resolved out of that locked set rather than by a separate read in front of it. `venues_concurrency_test.exs` is not sandboxed and proves the lock matters: without it, two concurrent revocations of two grants both succeed and orphan the venue.

A survivor only counts if it carries no revocation at all, not merely if it is live at this instant: a grant revoked at 13:00 is live at 12:00, and counting it at 12:00 orphans the venue from 13:00. A grant that already carries a revocation is `{:error, :not_found}` whichever instant asks.

What a grant may revoke is itself and its transitive descendants through `granted_by_grant_id`, walked with a recursive CTE so that a descendant hanging off an already-revoked link is still reachable. Everything else — an ancestor, a peer, another venue's grant, an id that names nothing — is `{:error, :not_found}`, so the refusal enumerates nothing. Revocation is **not** transitive in the other direction: closing a grant leaves the grants it issued live.

## The bridge

`engagements` is the single crossing between the zones (KTD2) and the only column anywhere outside the person zone that names a human. It is classified `:shared`, not `:employer` — the distinction is what lets the employer zone's "no foreign key to `people`" rule be absolute. Everything is reached through `HospitalityComs.Engagements`; `Engagements.Records` owns every query.

**Three callers, three roles, and the claim is none of them.** An employer session issues invitations, renews and ends engagements, and lists the venue's own, through `EmployerRepo` under a grant resolved on every call (`Venues.fetch_acting_grant/1`, made public in U5 so the check is not duplicated). A person lists their own engagements and attested entries through `Repo`, filtered by `person_id`. The **claim** runs as the application's own role under a `PersonScope`: it consumes an invitation, writes the bridge row, writes an attested entry `employer_role` holds no privilege to write, and enqueues the expiry job — no session on either side holds the privileges for all four.

**Activeness is derived.** `starts_at <= t < ends_at`, half-open, nothing stored. The table keeps a `period tstzrange GENERATED ALWAYS AS (tstzrange(starts_at AT TIME ZONE 'UTC', ends_at AT TIME ZONE 'UTC', '[)')) STORED` for the exclusion constraint alone; queries use the two endpoints. `AT TIME ZONE 'UTC'` is what makes the expression IMMUTABLE enough for a generated column.

**Three races, three different guards, and none covers another.**

- Two people redeeming one code produce engagements for *different* people, so nothing overlaps and the exclusion constraint is silent. The guard is a conditional `UPDATE` requiring exactly one affected row as the **first** `Ecto.Multi` step, with a unique index on `engagements.invitation_id` underneath. The loser gets `{:error, :consume, :already_claimed, _}`.
- Two overlapping terms are `engagements_no_overlap`, an `EXCLUDE USING gist` over `(person_id, venue_id, period)` needing `btree_gist` (its own earlier migration). It is **named**, and `Engagement` declares a matching `exclusion_constraint/3`; without the pair the violation raises through the transaction.
- Two concurrent renewals do not conflict with themselves, so `optimistic_lock(:lock_version)` is what makes the loser `{:error, :stale}`.

`engagements_concurrency_test.exs` proves all three are load-bearing by parking both racers on one Postgres row lock. **Build the racer tasks inside the barrier's closure** — `Task.async/1` starts a process immediately, so a list built at the call site races the barrier itself and the file flakes about one run in three.

**The expiry worker writes nothing to `engagements`.** It re-derives activeness and broadcasts only when false, so a job scheduled for an upper bound a renewal has since moved is inert — which is also why nothing has to cancel one. It could not enqueue atomically from a renewal anyway: renewal runs inside an `EmployerRepo` transaction and Oban writes through `Repo`, so a job inserted there would commit even if the renewal rolled back. Only the claim enqueues. `ExpireEngagement`'s args carry `{engagement_id, venue_id, ends_at}` and no person; `ends_at` is a uniqueness discriminator the worker never reads, so a renewal produces a different job while two sweeps over one unrenewed engagement produce one.

**The revocation broadcast is best-effort and says so.** `Phoenix.PubSub.broadcast/3` can answer `{:error, term()}`; `Engagements` logs it and answers `:ok` rather than propagating, because the revocation is the rejoin `join/3` refuses (KTD8) and this message is only the nudge that makes an already-powerless socket notice. Failing `end_engagement/2` over a broadcast would roll back a term that is genuinely closed in order to report that nobody was told. `Oban.insert/2` in the claim's Multi has the same shape: under advisory-lock contention it answers `{:ok, job}` with `conflict?` set and nothing persisted, so a claim can report success for an announcement that does not exist. Left as-is on purpose — the sweeper's moving window picks it up on the next tick, which is what the window is for.

**KTD17 is enforced from both sides and neither rule changed.** `Venues.revoke_grant/2` still refuses the venue's last live grant *row*; `Engagements.end_engagement/2` refuses its last active *grant-holding engagement*, under `FOR UPDATE` on the locked set. Folding them together would make a venue whose sole manager's engagement expired both unadministrable and revocable.

**"Holding an authority" means a grant that is live**, not a `grant_id` that is set. An engagement whose grant was revoked is neither a survivor that lets the real manager be ended nor a target that can never be ended itself; `Records.decision_set/4` reuses `EmployerGrant.live_at/2` so "live" cannot come to mean two things. It is a subquery in `where` rather than a join, because `FOR UPDATE` over a join locks `employer_grants` too, in an order `Venues.revoke_grant/2` does not share. `claim_invitation/2` asks the same question again in its own Multi step (`:conferrable`), because an offer is good for as long as its code is and the grant it confers can be revoked in between.

`end_engagement/2`'s **target set is "the term has not closed"**, one state wider than active, and it closes at the later of the caller's instant and the engagement's own `starts_at`. So an engagement claimed before its term opens can be ended, producing `ends_at == starts_at` — the empty range, active at no instant and overlapping nothing, so the person's dates are free again. Before that it was `:not_found` while still occupying the exclusion constraint for the whole term, so a claim made in error reserved somebody's dates and nobody could take it back. The widening is on the ending path **alone**: `list_engagements/1`, `fetch_engagement/2` and `renew_engagement/3` all still answer on `active_at/2`. An already-closed term, another venue's engagement and an id that names nothing are all still `:not_found`, so the refusal enumerates nothing.

**Oban** is configured in `config/config.exs` with a five-minute cron sweep, U10's hourly `RetentionSweeper` and #15's hourly `AccountReaper` sharing a `lifecycle` queue of one — at `0` and `30` past, because a concurrency of one means two jobs staged together simply queue behind each other — and `Oban.Plugins.Pruner` at seven days; **both `config/test.exs` and `config/dev.exs`** set `testing: :manual` — no queue runs, no plugin ticks, every worker in the suite is invoked by `Oban.Testing.perform_job/2`, and in `:dev` the only thing that runs a worker is `Demo.run_due_work/0`. The `:dev` half is not symmetry: see **Demo**. `oban_jobs` and `oban_peers` are in no zone; `boundary_test.exs` names them in its infrastructure exclusion list and asserts `employer_role` holds nothing on either.

**Three numbers that are a set, not three independent settings.** `ExpireEngagement`'s uniqueness is `period: :infinity` over `Oban.Job.states() -- [:discarded, :cancelled]`; `EngagementSweeper` looks back one day; the pruner keeps seven.

- The two exclusions are what make the sweeper a backstop. Spanning *every* state — which `Oban.Job.states()` does — means a job that exhausted its attempts suppresses its own replacement for ever, and suppresses the sweeper's identical insert too.
- `:completed` is deliberately **kept**, which is where this parts company with Oban's `:incomplete` shorthand. Under `:incomplete` a finished announcement stops suppressing as well and every expiry inside the sweep's window is re-announced on every tick. There is a test for each direction.
- The lookback must stay comfortably shorter than the pruner's `max_age`: the completed announcement is what stops the re-announcement, and pruning it while the term is still inside the window would produce exactly that. **That ordering was this sentence and nothing else until issue #42.** It is now a compile-time `raise` in `EngagementSweeper`, which reads the pruner's `max_age` with `Application.compile_env/3` — lib→config, never the reverse — and refuses to build when the lookback is not shorter. It cannot be a test in the ordinary sense and does not need to be: a build failure reaches every environment, where `config/test.exs`'s `testing: :manual` reaches none. (The configured value *is* readable in `:test`, contrary to the issue's premise — `testing: :manual` deep-merges and stops the plugin starting rather than removing the setting — so a runtime test was available and was declined as a second declaration of one relation.)

**The sweep is a window, not a floor.** `Engagements.list_expired/3` takes `(instant, since, limit)`, filters `since < ends_at <= instant` and orders `desc: ends_at, asc: id`. Filtering on `ends_at <= instant` alone under a limit pins the sweep to the same oldest rows for ever once more than `batch_size/0` engagements have ended — it keeps running, keeps reporting success, and never reaches a term that closed this morning. The index that serves it is `(ends_at, id)`; a `venue_id`-led one cannot, because the sweep is scoped to no venue. **Assumption on the record:** a term that closed more than a day ago is never swept again, which costs nothing because correctness never depended on the announcement.

**Oban's staging query is bound to real wall-clock time and `HospitalityComs.Clock` does not reach it.** Oban's engine asks `scheduled_at <= DateTime.utc_now()` inside its own code. So advancing `Clock.Offset` changes every membership query in the application *instantly* while a scheduled expiry announcement still waits for real time to arrive — and skipping that wait is exactly what the offsettable clock exists for. The suite steps around it by running workers through `Oban.Testing.perform_job/2`. **U11's demo controls must drive the sweep and the worker directly rather than advancing the clock and waiting for the queue.** Do not try to make Oban clock-aware to fix this.

**Three test files are not sandboxed:** `engagements_test.exs`, `engagements_concurrency_test.exs` and `workers/engagement_sweeper_test.exs`. All three call `EngagementsFixtures.real_connections/0`. The claim spans both repos' connections, and under the sandbox those are two transactions that cannot see each other's rows. They commit for real and purge on a `u5-venue` / `u5-person` prefix before and after each test. That is also why `boundary_test.exs` asserts the bridge's row-level security structurally and leaves the behaviour to `engagements_test.exs`.

**A claim code's lifetime is bounded.** `Invitation.max_code_validity_in_days/0` is fourteen days, the same bound `PersonToken.session_validity_in_days/0` puts on the other bearer credential in the tree, enforced in the changeset and by `invitations_code_expiry_within_bound`. There is still no way to withdraw a code early; the bound is what stops one outliving the venue's interest in it.

## Rooms and rosters

`shift_rooms`, `room_messages` and `roster_entries` in the employer zone, `venue_room_suspensions` in the person zone — the first table added there since U2. There is no `venue_rooms` table and no `shifts` table: a venue room is derived from a venue, a shift room *is* the shift. Nothing stores membership and no job maintains it (KTD6b); every membership answer is a query over periods, and moving the instant changes it with nothing having run.

**The venue room's roll is the venue's active engagements, suspensions included, and that equality is KTD18.** `Records.venue_room_members/2` deliberately does *not* apply `unsuspended/2`, so it returns the same set `Engagements.list_engagements/1` already answers with. A manager is a worker too — they hold an engagement like anybody else — so one caller holds an employer scope and a person scope at the same venue; a roll that subtracted suspensions would differ from `list_engagements/1` by exactly the opt-out set, and the invisibility the person zone buys would be recoverable by subtraction with both tiers intact. `rooms_test.exs` pins the two lists returning the same ids. **Do not re-add the filter.** Suspension governs the suspended person's own access alone: `venue_room_membership/3` and `venues_of_person/2` keep `unsuspended/2`, so they cannot read, send, or see the room in their own list, and nobody else's answer changes. Nothing is lost — the venue room carries full history, so they read what was said while they were away the moment they resume.

**History is bounded in the context, and the bound is an *extent* rather than a number.** `list_venue_room_messages/2` and `list_shift_room_messages/2` were `Repo.all/1` over every message a room had ever held; both now answer a `Rooms.MessagePage` — the most recent `Rooms.recent_message_limit/0` (fifty), oldest first *within* the page, plus `complete`. The unbounded read is a third arity taking `:all`. **No caller may pass a number**: a route passing `limit: 50` leaves the unbounded function one forgetful caller away from production, which is how it came to be the only read there was. `complete` is answered by selecting one row more than the page, so it is exact at the boundary rather than inferred from a length — and it is what makes the bound observable to a test at all, because a full page and a full history of the same length are the same list.

`Records.most_recent/2` re-orders ascending in SQL *around* the descending scan, so the page's own order is a property of the query rather than of whoever remembered to flip it. The probe row is therefore the **oldest** of the batch, which is why `MessagePage.bounded/2` takes from the end: taking from the front hands back the oldest fifty while satisfying every count assertion, and it is the one mistake here that is silent. `rooms_test.exs` names the first and last bodies rather than counting, against a fixture of fifty-one.

**Four person-side HTTP routes**, on the authenticated pipeline, in `HospitalityComsWeb.RoomController`: `GET /api/venue-rooms`, `GET /api/venue-rooms/:venue_id/messages`, `GET /api/venues/:venue_id/shift-rooms`, `GET /api/shift-rooms/:shift_room_id/messages`, with `?extent=all` and no `limit`. Two of them are lists you need *before* you have a room to ask through, which is why none of this is a channel event.

The shift-room list hangs off the **venue**, not the venue room, and that is KTD18 rather than taste: a suspended person is out of the venue room and still on their shift rosters, so a path nested under the venue room would invite a membership gate that extended suspension to shift rooms. `Rooms.list_readable_shift_rooms/2` is the venue-filtered arity — the filter is a parameter on `Records.readable_shift_rooms/3` rather than a `where` at the call site — and it preloads the shift type, because a `ShiftRoom` has two instants and no display name, so a client without it renders uuid prefixes. The label is the type's name plus the term, composed on the client: formatting a shift time means choosing a timezone, `venues` carries one and the worker's device carries another, and the worker is the reader.

**A message carries its author's name and what they do at this venue, both joined on every read** (#66, #65). `RoomChannel.rendered/1` gained `author_display_name` and then `author_role_label` and is still the single spelling, so both transports and both room kinds moved together each time. Neither is a column on `room_messages`: a stored copy is denormalised, a stored *name* is a person's name in an employer-zone row (KTD2 broken), and either would make erasure an unbounded write. `Records.with_author/1` — renamed from `with_author_display_name/1` when it stopped doing one thing — joins `room_messages → engagements → people` with **no activeness predicate anywhere**, which is the whole decision: a venue room keeps full history, so a message whose author's term closed is ordinary, and a client-side join against the room's current roll has nothing to find for one. Measured: adding such a predicate kills 4 tests and nothing else.

**#65's join was free and its own issue did not know that.** It weighed client-side against server-side and hedged on "costs a join in `Records.venue_room_messages/2`"; by the time it was built #66 had already added that join, and `role_label` is a column on `engagements`, which the query binds on the way to `people`. So the label is one entry in an existing `select_merge`. Measured: dropping it kills **23**, and dropping `with_author/1` from the two read paths kills **12**.

**Three values on a rendered message and no two do the same work.** The name is global and not unique; the label is venue-local and not unique either — a venue can hold two Bartenders; `author_engagement_id` is the only one of the three that tells two speakers apart, and dropping it kills 7. An **erased author renders both constants** — `Former colleague · Former team member · 4a3f…` — deliberately: they are two facts about two things, `Lifecycle.erased_display_name/0` and `erased_label/0` are separate constants with no asserted relation, and suppressing one would be the only special case in a render function that has none. Collapsing the two constants into one kills 4.

**Both sends read the row back through that same join**, and the two fields are there for different reasons. For the **name** it is a correctness requirement: `ChannelAuth.person_scope/1` builds `%Person{id: person_id}` and nothing else, so a scope-derived name is correct over HTTP and `nil` on both channels — 13 tests, all of them channel sends. For the **label** it is not — both sends already resolve a whole `Engagement` row in the same transaction, so `engagement.role_label` would be the same string on both transports, and **that mutation kills 0, predicted before it was measured**. It is read back anyway because the query is already being issued and one source behind one rendered shape is what four separate defects in this tree came from not having. `rendered/1` heads on both fields being binaries so that a read path which forgot the join crashes rather than putting a `null` on the wire; each half of that guard is pinned by one test in `venue_room_channel_test.exs` and by nothing else.

Every refusal is `404` with one sentence — `:not_a_member` and `:not_found` each already cover several states, and a `403` would confirm the room exists. A malformed path id is the same `404` rather than the `500` an uncast id raises out of Ecto, through `HospitalityComsWeb.EntityId`, which is `ChannelAuth.topic_id/1`'s rule moved out so a path parameter is not a fourth caller of a function named after a topic suffix; the three channels keep the function they call and `topic_id/1` delegates. Messages are rendered by `RoomChannel.rendered/1` rather than a second spelling, so a message has one key set whichever transport carried it and nothing on these routes names a person. The login rate limiter is deliberately **not** extended to them: they need a live session, they write nothing, and their cost is bounded in the context.

**`room_messages` has a row-level security policy and no database tier behind the query filters.** `employer_role` holds nothing on the table and the policy is not `FORCE`d, so the only accessor — `Repo`, which owns it — is not bound. `FORCE` is not available: the predicate raises wherever `app.employer_id` is unset, which is every person-side read, and `Repo` connects as `postgres`, a superuser, which bypasses row-level security regardless. What is real is the composite keys: `room_messages_author_fkey` MATCH FULL into `engagements (id, venue_id)` and `room_messages_shift_room_fkey` into `shift_rooms (id, venue_id)`, which is why `Records.shift_room_messages/1` is safe with no venue filter and `venue_room_messages/1` rests on the `venue_id` its caller's resolved engagement carries. `*_enable_room_row_level_security.exs` says all of this; do not restore the "belt and braces" reading.

**`roster_entries.joined_at` and `left_at` are `:utc_datetime_usec` over `timestamp(6)`, alone in the schema, and neither is truncated.** Flooring the upper bound closes a period before the removal happened and shortens an overlap that has already elapsed, which is the one thing KTD6b says no write may do; flooring the lower bound backdates the rostering. `timestamp(0)` *rounds* where Ecto's `:utc_datetime` truncates, so the column type and the changeset had to move together. `venue_room_suspensions` deliberately stays whole-second: both its bounds move the person's own absence in the person's own favour and change nobody else's answer.

**Removal is one conditional statement, not a read then a write.** `Rosters.remove_from_roster/3` issues `UPDATE … WHERE left_at IS NULL` and answers `{:error, :not_rostered}` when it matches nothing — the same answer a period closed a moment ago already got. Before it, two managers removing at two instants both succeeded and the row carried whichever `left_at` committed last. There is no `lock_version` here on purpose: a renewal is a repeatable mutation where `:stale` is the only honest answer, while closing a period happens once.

**An `EXCLUDE` conflict between two uncommitted inserts is a deadlock, not a violation.** Measured at `40P01` with two live racers on `roster_entries_no_overlap`; `engagements_no_overlap` has the same property. The changeset error the moduledocs promise is what arrives when the conflicting row is committed, which is the ordinary case. `rooms_concurrency_test.exs` builds its two insert races that way — a caller parked on a `SHARE` lock, having demonstrably passed its friendly check against an empty table, then meeting a committed conflict — and says why.

**`Rosters.add_to_roster/3` takes an engagement whose term has not *closed*** — active or not yet started — which is `EngagementRecords.not_ended_by/2` and is exactly the set `end_engagement/2` targets, widened for the same state and for the same reason (#24). It used to require *active*, so next Monday's hire could not go on next Tuesday's shift today: the reasoning ("somebody who no longer works there does not work the shift") is about the closed case, and the same predicate excluded the not-yet-open one as a side effect. Nothing depended on the write-time check — `shift_room_members/2`, `shift_room_readers/2` and `readable_shift_rooms/2` all intersect with `active_at/2`, so the entry confers nothing until the term opens — and `rosters_test.exs` now asserts that rather than asserting it in prose. **The room in that test is open at both instants on purpose:** written against next week's room every "before" assertion passed because the room was shut, and deleting `active_at/2` from `shift_room_members/2` left it green.

Two residues, both deliberate. "Not closed" is `ends_at > instant`, so it also admits an engagement *ended before it opened* (`ends_at == starts_at`, in the future); that entry is active at no instant, so it confers nothing, and excluding it would take a non-emptiness clause and give `add_to_roster/3` a different set from `end_engagement/2`. And the refusal stays `{:error, :not_found}` for a closed term, another venue's engagement and an id that names nothing alike — enumeration-resistance (AE1), since otherwise a caller walks a venue's engagement ids one refusal at a time. Whether an operator inside their own venue deserves a distinguishable reason is a product question #24 raises and nobody has answered.

**Three more test files are not sandboxed:** `rooms_test.exs`, `rosters_test.exs` and `rooms_concurrency_test.exs`, all through `EngagementsFixtures.real_connections/0`, for the reason U5's three are.

## Peer graph

`connection_requests`, `peer_connections` and `peer_messages`, all **person zone**, all created by `*_create_peer_graph.exs` and reached only through `HospitalityComs.Peers`. There is no `peer_visibility` table and no `conversations` table: `Peers.Visibility` and `Peers.Conversation` are plain structs derived on every read, the way `Rooms.VenueRoom` is.

**The classification was not a judgement call.** Each of the three holds at least one foreign key to `people` — three on `connection_requests` (`requester_id`, `addressee_id`, `blocked_initiator_id`), three on `peer_connections` (`person_a_id`, `person_b_id`, `disconnected_by_id`), **one** on `peer_messages` (`author_id`) — and none holds an employer key of any kind, so a peer table anywhere but the person zone would be a second crossing and `boundary_test.exs`'s positive form — `engagements` is the *only* table outside the person zone that references `people` — would fail. `employer_role` holds nothing on any of them, `EmployerRepo`'s backstop raises naming the table, `EmployerSocket` routes no peer topic, and every `Peers` function heads on a `PersonScope`. `peers_test.exs` asserts **three of those four** against a conversation that actually exists — the grant tier, the backstop, and the scope split — because `boundary_test.exs` cannot populate one. The `EmployerSocket` routing claim is `sockets_test.exs`'s and involves no conversation at all.

**Visibility is `[max(their two starts_at), min(their two ends_at) + 30 days)`, derived per pair per venue.** "Co-rostered" is read as *concurrent engagement at one venue*, not as a shared shift: the plan says "per pair per **venue**" and "the first of the two **engagements** to end", and a shift-level reading would leave the engagement endpoints doing nothing. It also lands where U6 already is — the venue room's roll is the venue's active engagements, so the people a worker can see are the people they are already in a room with, plus thirty days. The tail keys on the **first** engagement to end, so somebody who left in January stops being visible to a colleague still employed there.

`Records.co_engagements/1` writes the interval as four comparisons rather than `GREATEST`/`LEAST` — `max(a) <= t` is `a1 <= t and a2 <= t`; `min(b) + 30d > t` is `b1 > t-30d and b2 > t-30d` — so the predicate stays in plain Ecto and the thirty days live in one function, `Visibility.cutoff/1`, that the rendered struct calls too. Four more clauses in front of those say the two terms overlap at all and that neither is empty; **all eight are load-bearing**, and `end_engagement/2` producing `ends_at == starts_at` is why the emptiness pair exists. `co_engagements/1` tests each term separately and `own` is always the asking person's, so a test that only ever asks from one side exercises one of the two — `peers_test.exs` now asks from both.

`peers_test.exs` compares the SQL spelling against the struct over a matrix of term pairs and instants, which is U6's manoeuvre against the generated `open_period` column, and the comparison is against **`Visibility.visible_at?/2`** rather than `covers?/2`. That distinction is the whole value of the test: `covers?/2` is only the containment half, so a matrix that called it and restated the overlap half in the test file was comparing the SQL against its own test's idea of it. `Visibility.concurrent?/1` is the other half, exported for exactly that reason, and the matrix carries a **strictly positive gap** — two terms that miss each other by less than the thirty-day tail, which `covers?/2` alone calls visible.

**A gap of one second is enough to be co-rostered, and there is no minimum.** Two people whose engagements overlap by a single second are visible to each other for thirty days past the earlier end, and can form a connection that is permanent. That is the rule as specified rather than an oversight — visibility is "concurrent engagement at one venue" and nothing in the origin asks for a duration floor — but it is worth stating, because "worked together" reads as more than it enforces.

**The peer list carries the counterpart's display name** (#66), beside the `person_id`, the shared venue and the role label it already had. Strictly less identifying than the key already there, and the audience is exactly the audience the venue room's roll discloses to. `peers_test.exs`'s "discloses no email address" assertion is unchanged and unweakened, with an exact key set beside it — that pin is what fails when a field is *added*, which is the direction an address would arrive from.

**#73 closed the rest of it, and the deferral note was wrong about how.** `Conversation`, both connection-request shapes and `PeerMessage` all carry the counterpart's name now — five virtual fields filled by three joins in `Records`, `with_pair/1`, `with_parties/1` and `with_author/1`, which are `Rooms.Records.with_author/1`'s manoeuvre and carry its rule: **no activeness predicate and no `erased_at` filter on any of them**. Here that is R15 rather than a copy of #66's reasoning — a connection outlives the visibility that produced it, so a name that lapsed with co-rostering would blank the heading of a conversation two people are still having, and a lapsed *request* is still in its requester's list and is exactly the row they are trying to make sense of.

The expected fix was to widen `Records.connections_of/1` and `connection_of/2`, and **checking the four callers refuses it**: `disconnect/2` composes `connection_of/2` into an `update_all`, whose `RETURNING` cannot reference a joined table, and `locked_open_connection_of/2` adds `FOR SHARE`, which over a join would lock the joined `people` rows too — the trade `EngagementRecords.decision_set/4` already refuses by using a subquery in `where`. So the join is a separate composable applied at the reads that render, and the two statement-shaped callers keep the query they have.

**Every write reads its own row back through the query a list read uses**, which is `Rooms.naming/1`'s shape and its reason: neither `Multi.insert/4` nor `update_all … RETURNING` can name a joined column, and a scope-derived name is correct over HTTP and `nil` on both channels (#66, measured). Four read-backs — `request_connection/2`, `decline_request/2`, `accept_request/2`, `send_message/3`. The two request ones go through `Records.request_by_id/1` rather than `request_of/2`, because that query's `superseded_at IS NULL` can stop matching between a decline's `UPDATE` and its read-back and a `one!` raising on this channel takes every one of that person's conversations down.

**An erased counterpart needs no special case and has no messages.** Erasure overwrites `display_name` with `Lifecycle.erased_display_name/0` in the statement that nulls the address, so the conversation heading and a pending request from them read the constant with nothing having visited `peer_connections` or `connection_requests`. There is no erased-author *message* to render, though: erasure deletes the erasing party's own peer messages and keeps the connection and the request rows (the row *is* KTD19's block). `peers_test.exs` asserts that rather than omitting the case.

**`Peers.list_reachable_peers/1` is the list form of `visible?/2 or connected?/2`** — the pair `Profiles.fetch_peer_profile/2` gates on, written once so the gate and the list cannot come to mean two things. One entry per **person**, deduplicated on `person_id` and never on the name, where `list_visible_peers/1` is one per **venue** because it carries the venue. A closed connection's counterpart is not on it. It exists for #73's disclosure audience picker, and the connected half is what makes the remedy the peer-disclosure residue names — one `set_disclosure/4` row — reachable from the surface that needs it: the person a worker most wants to hide an entry from is one who is connected and no longer co-rostered.

**`list_visible_peers/1` is one entry per counterpart per venue.** It used to be one per overlapping *pair of engagements*, so two stints at one venue produced the same `person_id` twice with two `visible_until` values and possibly two role labels, and the channel renders the list verbatim. Merging is safe here and nowhere else: every interval in that list contains the asking instant, so their union is an interval with no gap to lose. `Visibility.merge_stints/1` folds them to `[min(from), max(until))` and keeps the label from the longest-running stint. Nothing authorises off the list — `visible?/2` and `request_connection/2` both ask `Records.visible_between/3`, which still ranges over every pair.

**A pair's whole state is one `connection_requests` row.** `superseded_at IS NULL` with a partial unique index on the generated `(pair_low_id, pair_high_id)`, so "the pair's current row" is a database guarantee. Reading "the latest row" by `(requested_at, id)` was rejected and the reason is specific to this tree: the clock is injectable and tests pin it, so a decline and the counterpart's answering request can share an instant exactly, and `id` is random on a `binary_id` schema — the tie-break would be a coin toss in precisely the case KTD19 is about.

**KTD19's block is `blocked_initiator_id` on that row.** The party who refused keeps the initiative; the party who was refused does not. A decline blocks the requester; a disconnect blocks the counterpart of whoever disconnected, because disconnection is the origin document's only stated remedy for harm and a symmetric reading hands it back to the person it was used against. It is a column rather than a rule over engagements, and that is the whole of "the block survives new co-rostering". Blocks are read off the *current* row only — KTD19 governs "the next request", and accumulating them would make a pair who each declined the other once permanently unreachable to both.

`connection_requests_decline_blocks_requester` is the check constraint that enforces the decline half, and it does so with `IS NOT DISTINCT FROM` rather than `=`. **A CHECK is satisfied by NULL and `NULL = requester_id` is NULL**, so the plain equality passed for a declined row carrying no block at all — the one row the constraint exists to refuse — and the invariant rested on `decline_request/2` writing both columns in one statement. `peer_connections_closure_complete`, in the same migration, was NULL-proof from the start via paired `IS NULL` comparisons.

**`request_connection/2` decides and supersedes in one statement**, and that is KTD19 rather than tidiness. As two statements the block was defeatable by racing: under `READ COMMITTED` a `SELECT … FOR UPDATE` that parks on a row another transaction is superseding re-evaluates *that row* on release and correctly finds it no longer current — but the replacement the other transaction inserted was never in that statement's snapshot, so the blocked party read "nothing current", was permitted, and a following `update_all` with a fresh snapshot found the replacement and superseded it. Both callers were told `{:ok, …}`, one request was silently lost, and the block was consulted against a row that had already been answered. `update_all … RETURNING` removes the second snapshot: whatever is invisible to the decision is invisible to the supersede, so the insert meets the partial unique index instead.

**`send_message/3` re-resolves the conversation under `FOR SHARE` inside a transaction, and announces after the commit.** An unlocked read followed by an insert stored a message that arrived while the other party's `disconnect/2` was committing — the insert waits only on the foreign key's `FOR KEY SHARE`, which a row whose id has not changed satisfies — and then pushed it to the person who had just cut contact, into a history their own `list_messages/2` will never show them. `FOR SHARE` conflicts with the `FOR NO KEY UPDATE` the disconnect's `UPDATE` takes, so the send parks and then matches nothing. **`Rooms.send_venue_room_message/3` grew the same shape in U10, for a different boundary**: it resolves the *venue* under `FOR SHARE` and refuses `:room_closed`, because a send racing `Lifecycle.close_venue/2` commits a message the closure's stamping statement has already passed over, and a venue-room message with a null deadline is one nothing can ever delete. It is still unchanged with respect to a racing *engagement* end — there the loser is a stale message in a venue room with no remedy semantics attached to it. Here and in `Peers` the boundary is the point.

**`:lapsed` is derived, so it can un-lapse.** A pending request whose pair cannot see each other at the asking instant reports `:lapsed` and cannot be accepted; it *can* still be declined, because an addressee may always say no and refusing would leave a row nobody could clear. If the pair is co-rostered again the same row reports `:pending` again. That is the consequence of deriving rather than storing, written down as a decision: a stored `expired_at` would have needed a job visiting every outstanding request whenever any engagement moved.

**Visibility gates discovery and requests, and gates nothing about a conversation that already exists.** A connection survives both engagements ending and both parties keep writing to it — which is what makes the demo's payoff moment reachable. After a disconnect each party reads *their own* messages and only their own; nothing is deleted (KTD21), and `peers_test.exs` asserts the row count as the control for that.

**Two partial unique indexes carry the races.** `connection_requests_one_current_per_pair` is what makes crossed simultaneous requests resolve to one; `peer_connections_one_live_per_pair` is underneath the one connection they then produce. `peers_concurrency_test.exs` is not sandboxed and proves both, plus the conditional closes on accept and disconnect. Unlike U6's insert races it can carry two real racers: a unique index makes the second inserter wait and then raise `unique_violation`, where an `EXCLUDE` conflict between two uncommitted inserts deadlocks.

**Two of its five races name an *ordering* rather than a collision**, and use a different helper for it. KTD19's block and R15's disconnect are each defeated by one interleaving of two callers and not by the other, so `ordered/2` starts the racers one at a time and waits for each to park before starting the next; Postgres serves the waiters on one tuple in arrival order. Raced symmetrically through `race/3` both tests would pass half the time against the bug they name, which is worse than not having them.

**Queries live in `Peers.Records` and `peers_test.exs` now pins that structurally**, out of the compiled `imports` chunk the way `person_zone_test.exs` reads repo calls. `Ecto.Query.Builder` and `Ecto.Query.Builder.From` may appear in no module of the `HospitalityComs.Peers` namespace but `Records`; `Filter`, `Select` and `Update` are permitted in the context, because they are the `where`, `RETURNING` and `SET` of a write applied to a query `Records` handed it and none of them can name a schema. The rule was already broken when the check was written — `disconnect/2` built its block update inline — and nothing had noticed.

**Two more test files are not sandboxed:** `peers_test.exs` and `peers_concurrency_test.exs`, for U5's reason — visibility is derived from engagements, and an engagement spans both repos.

### What U9 and U10 inherit, and one thing nothing caps

**A requester cannot withdraw an outstanding approach.** Declining blocks the requester by design (KTD19), so there is no *non-blocking* way to take an approach back: it stays pending and re-arms years later when co-rostering returns. A `withdraw_request/2` — one conditional `update_all` setting `superseded_at` and writing no block, leaving the pair at zero current rows, which `permitted(nil, false, _)` already accepts — is the obvious shape and is deliberately **not** built here. It is not in the issue's scenarios, and it is a product decision rather than a mechanical addition: withdraw-and-resend defeats the one-outstanding-request throttle, so whether it exists is the same question as whether requests are rate limited (below).

**Nothing caps request fan-out.** One actor at a large venue can send a distinct request to every other worker there. Each recipient can stop it once, by declining — which blocks the sender permanently, so the graph self-heals per pair — but nothing bounds the number of outstanding requests one person may hold. This belongs with **issue #15**, which already covers rate limiting and abuse control for `POST /api/log-in`, and not with a peer-specific counter.

**U10 needed a disconnect it could drive, and built one.** `Peers.disconnect_all/3` takes the caller's repo, a person id and an instant, closes every live connection that person is a party to in one conditional `update_all … RETURNING`, and blocks each counterpart — KTD19's disconnect half applied from the erasing party's side. It announces nothing; `Lifecycle` calls `Peers.announce_disconnection/1` after the commit, which is the split `Engagements` already has between closing and announcing. The remedy semantics stayed in `Peers` rather than being reimplemented in `Lifecycle`; only the deletion of the erased person's own messages is `Lifecycle`'s (KTD21).

**`Peers.block_counterpart/4`'s `{1, _}` match is gone, and the condition that made it a hazard was never created.** Erasure deliberately **retains** `connection_requests` rows: the row *is* KTD19's block, and `peer_connections.request_id` is `NOT NULL ON DELETE RESTRICT`, so deleting one would destroy the counterpart's protection and orphan the connection. `lifecycle_test.exs` pins that the rows survive. The match itself became `{:error, :request_gone}`, enumerated in `disconnect_failure()`, so an invariant held by a schema decision fails loudly rather than crashing a transaction if that decision is ever revisited — `peers_test.exs` proves it by dropping the foreign key for one call and restoring it idempotently.

**A crash on this channel takes every one of that person's conversations with it** (KTD10, deliberate). One GenServer carries the whole peer surface, so an unhandled exception in any `handle_in/3` drops all of them at once rather than one. No current path triggers it — every event answers rather than raising, the terminal clause is tested, and `handle_info/2` has a catch-all — and it is the cost of multiplexing rather than a defect to fix.

## Profile and disclosure

`declared_entries` and `attested_entry_disclosures` in the person zone, `correction_requests` in the employer zone, all created by `*_create_profiles.exs`; `attested_entries` was already there since U5 and U9 changed nothing about it. Everything is reached through `HospitalityComs.Profiles`, and `Profiles.Records` owns every query — **including every write**, so the context reaches *zero* Ecto query builders, which is stricter than `Peers` manages and is asserted structurally in `profiles_test.exs`.

**A declared entry's label bound is 160, not 120, and the correction is issue #42's.** `DeclaredEntry` said *"the same bound `engagements.role_label` carries"* over a literal 120 while that column carried 160, and had since the unit shipped — the strongest evidence in the tree that an uncheckable linking sentence drifts. `*_widen_declared_entry_labels.exs` moves both `declared_entries` bounds (`organisation_name` travels with `role_label`, because one module attribute governs both validations), and the module now reads `Invitation.max_label_length/0` instead of restating it. Its `down` narrows and would fail with `check_violation` against a stored label over 120; that is stated in the migration rather than dodged with `NOT VALID`, and it cannot fire here because such a row is only writable after the migration.

**The employer reads an attested entry only through a view.** `employer_visible_attested_entries` and `employer_visible_correction_requests`, owned by the login role that owns the base tables, granted `SELECT` and nothing else, `security_barrier = true`, and **not** `security_invoker` — with it on, the view would resolve base-table permissions as its *caller*, and `employer_role` holds none, so KTD3's mechanism would be inverted. All three properties are asserted; measured, turning `security_invoker` on breaks 25 tests. The `security_invoker` assertion reads the reloption's *value*, not its presence: an explicit `security_invoker = false` is the default by another spelling, and refusing it would be a false failure.

It is **not** true that the employer never touches a table. `list_venue_corrections/1` and `resolve_correction/3` read and write `correction_requests` through `EmployerRepo` on the base table, under the RLS policy on `venue_id` and a column-scoped `UPDATE`. KTD3 is about the rule a grant cannot express — per row, keyed on the reader; a `WHERE venue_id = ?` is one a policy can, and a venue's own inbox is its own data.

Every column on those views has a reader in `Profiles.Records`, and that is a rule rather than an accident: `boundary_test.exs` pins both column lists, so a column with no consumer is a permanent employer-facing surface that survives by default. `viewer_venue_id` (both views) and the corrections view's `attested_entry_id` were dropped for exactly that — the first restated `app_current_employer_id()`, which the caller supplied, and the second was a unique function of `entry_engagement_id` sitting beside it.

**KTD3 is stronger than its own argument here, and the reason is a measurement.** Its stated case was that row-level security "has to be `FORCE`d and must not run as table owner; a view has no equivalent switch to forget". On this deployment `Repo` connects as `postgres`, for which `rolsuper` is true — and a superuser bypasses row-level security whether or not a policy is `FORCE`d. So a per-row RLS rule on `attested_entries` would read as a tier in a migration and provide none. `boundary_test.exs` asserts `rolsuper` rather than assuming it, because if that ever stops being true the reasoning changes.

**The concurrency default is a comparison of two stored periods and names no instant.** An entry attested by venue A is hidden from venue B when the engagement it attests *overlapped* any engagement the same person held at venue B — `NOT EXISTS` over every stint, with the two non-emptiness clauses U6 measured and U8 needed. That single property is what makes two of the unit's requirements true at once: "changing an engagement's dates corrects the default automatically" holds because nothing is materialised, and "a hidden entry remains hidden after it stops being concurrent" holds because overlap is a fact about two periods rather than about now. **A default written as "concurrent at `app_current_instant()`" passes almost everything and re-discloses a second job at the moment it ends**, which is the leak the default exists to prevent; `profiles_test.exs` has the test that catches it, measured.

What *is* time-derived is which workers an employer may see at all: the people holding an engagement at its venue active at the scope's instant. The employer names a worker by **`viewer_engagement_id`**, their own engagement at their own venue. **The view exposes no `person_id`** — that is U9 acting on the ledger entry below.

**`app_current_instant()` is compared as `AT TIME ZONE 'UTC'`, and it is not decoration.** Ecto's `:utc_datetime` is `timestamp` *without* time zone, while the function returns `timestamptz`; comparing the two makes Postgres convert using the session's `TimeZone`, which nothing in this application sets. Measured under `America/New_York`: the same comparison answers `false` unconverted and `true` converted. This server's default is `Etc/UTC`, so it would have gone unnoticed. Any future comparison of a stored instant against that function needs the same conversion — it is the manoeuvre `create_engagements` already uses for the generated `period` column.

**Ownership on the disclosure ledger is a key, not a check.** `attested_entry_disclosures` carries `person_id` and `(engagement_id, person_id)` is a MATCH FULL composite key into `engagements (id, person_id)` — the unique index that makes it referenceable is created by `create_profiles.exs`, because `create_engagements` is on `main`. It is the person zone's reading of the discipline every employer-zone table already has through `engagements (id, venue_id)`, and it was the one ownership rule in the tree resting on application code alone. `set_disclosure/4` still asks first and the two are not redundant: the check produces `{:error, :not_found}` rather than a foreign-key violation, and the key is what makes the check's absence not a hole. Not a second crossing — the table is person zone and `person_id` references `engagements`, not `people`.

**Two indexes that are not decoration.** `(audience_person_id, disclosed)` is what serves the peer read's four subqueries per profile — the partial indexes lead on `engagement_id` and cannot — and it is also the index `audience_person_id` needs as an `ON DELETE RESTRICT` key, which is U10's problem the day it arrives. `(engagement_id, decided_at, id)` serves the worker's own read of the ledger.

**`attested_entry_disclosures` is the first person-zone table with an employer key**, and it is deliberate rather than drift. The audience of an employer disclosure *is* a venue and no spelling of that avoids reaching one; naming it through one of the person's own engagements re-discloses a hidden entry the moment they take a *new* engagement at the same venue, unless the view resolves the venue off it anyway — at which point the venue is one join away and the uniqueness guarantee is gone. Putting the ledger in the employer zone is the real alternative and is the worst of the three: `WHERE audience_venue_id = <me> AND disclosed = false` is the list of workers concealing something from a venue, which discloses strictly more than the entries do. So it is person zone, `employer_role` holds nothing on it, and the only path to the rule is a view returning the *result* of applying it.

**The standing incompleteness notice is a UI constant and two tests keep it one.** `Profiles.incompleteness_notice/0` is arity 0, so it cannot depend on the worker it is shown beside; and a worker concealing an entry produces an employer read identical in length and shape to one who has never worked anywhere else. The views' column lists are pinned, so a `hidden_count` cannot be added without a failure.

**The behavioural half of that was a control that could not control.** It compared `Map.keys/1` of two `%VisibleEntry{}` structs, which `defstruct` fixes at compile time — invariant under every possible difference in content, so an oracle introduced at the *render* layer was caught by nothing but the view's column pin. Measured: a `hidden_count` on the view, selected in `Records` and carried on the struct, reported 1 against 0 and that assertion passed. It is now a literal field list written in the test file plus an equality over the values with only the two entry ids dropped, and each half was measured against the same mutation. Fifth "control that does not control" this project has produced; when extending that file, assert against something written down rather than against the other side of the comparison.

**A person cannot edit an attested entry and there is no function that would.** `profiles_test.exs` pins the module's **whole export list** against a literal, because the earlier form — no exported function whose name contains "attested" except the one read — is satisfied by `edit_entry/3` or `restate/2`, which are the two spellings a writer would most plausibly arrive under. The remedy is `request_correction/3` — written by the *worker* through `Repo`, because `employer_role` holds no `INSERT` there and a session that could manufacture a complaint could then resolve it. Resolving writes no entry and cannot: accepting is an acknowledgement, and any real correction is a change to the engagement through `HospitalityComs.Engagements`.

`resolve_correction/3` filters `requested_at <= scope.now` in the conditional update *and* in the diagnostic that says why it matched nothing. Without it, `correction_requests_resolved_after_requested` arrives as a raw `Postgrex.Error` out of a function whose spec enumerates three atoms — an `update_all` carries no changeset, so nothing can turn the CHECK into one. Reachable through `Clock.Offset`, which U11's demo controls drive. The refusal is `:not_found`, because at the instant being asked about the request has not been raised.

**`VisibleCorrection` really is one shape for four readers now.** `Records.venue_corrections/1` had no `select:` and returned `CorrectionRequest` structs, so `resolution` was `"declined"` on the attesting venue's path and `:declined` on the other three, and the id arrived under `id` rather than `correction_request_id` — with `profiles_test.exs` asserting both spellings two lines apart. Third occurrence of that defect class in this tree (U8's `sent_at`/`at` was the second).

**Nothing in `Profiles` answers an Ecto schema, and that is now the rule rather than four modules that happen to agree** (#36). Four render structs — `VisibleEntry`, `VisibleCorrection`, `VisibleDeclaration`, `VisibleDisclosure` — and every one names its entity `<entity>_id`. U9 had two of them, so `DeclaredEntry`, `Disclosure` and `CorrectionRequest` went back as schemas saying `id` and one profile carried two conventions. "Four readers, one shape" was also a claim about *readers*: `request_correction/3` and `resolve_correction/3` both answered the schema, so the same entity was `id` with `resolution: "declined"` when written and `correction_request_id` with `resolution: :declined` when read — and the suite asserted `"declined"` from the writer four lines above `:declined` from the readers, which is the same divergence U9's own review had just removed from the other half. `VisibleCorrection.of_request/1` is the writers' door; it builds the row and delegates to `new/1`, so the field list and the string-to-atom conversion each have one spelling.

`new/1` means "from a selected row" and `of_<schema>/1` means "from a schema struct" — the split `Peers` already has between `Visibility.new/1` and `Conversation.of_connection/2`. Ecto schemas stay in the **error** half of every spec: a changeset is about the row a write failed to make, and its field names are the schema's.

`VisibleDisclosure` renders the audience as `audience_kind` (`:venue` or `:person`) plus `audience_id`, never the table's two nullable columns and never `Disclosure.audience/0`'s tuple. The columns put the XOR on the wire for every consumer to re-derive; the tuple cannot survive a JSON encoder, so whoever put it on a transport would split it there — and the split done twice is the defect again. U12's `client/src/features/profile/contract.ts` asks for exactly these spellings and its decoders **refuse `id`**, so this was a server change with no client change beside it.

**Peer disclosure has two halves and the second one is the venue's rule.** A peer sees an entry unless the worker named that peer and said otherwise, because the venue room's roll already told them the venue and the role label — *and* unless a venue that binds that peer would hide it. `Records.peer_disclosure/4` is the whole predicate and it composes over both peer reads, entries and correction requests alike, because R16 makes a request visible to any viewer of the entry it contests and a rule reaching one and not the other hands back the worker's own words about what it just withheld.

**Why the second half exists, and it is not defensive.** An employer session is a person session plus a venue, so a venue's manager necessarily holds an engagement there → is co-rostered with every worker at that venue → is a *visible peer*. With the peer default simply "disclosed", the concurrency default the employer view enforces was recoverable by asking the same question through the peer door: no grant, nothing manufactured, and no consent step, since the gate is visible **or** connected. It was invisible because every test in the file handed the employer scope and the peer scope to two different people; `profiles_test.exs`'s "the manager who is also a peer" block gives both to one.

The predicate is `concealed_from/3`: hidden when there is a venue V binding the viewer, V is **not** the entry's own venue, and the subject holds a stint at V overlapping the entry's term — the view's overlap clause for clause, the two non-emptiness comparisons included, each with its own test on this side because a mutation of either killed nothing before. `stint.venue_id != subject.venue_id` is the view's own-venue branch: an entry a venue attested is always visible to the people who work there. A viewer bound at two venues is bound by **both**, deliberately — showing what the more permissive of the two would show is how somebody with two jobs becomes a channel out of the stricter one.

**A venue binds the viewer two ways and neither contains the other.** They work there at the instant (`venues_worked_at/2`, which is `EngagementRecords.active_at/2` and not a second spelling), **or** the venue is what makes the two of them visible to each other at the instant (`Peers.Records.visible_venue_ids/3`, `co_engagements/1` projected onto the venue — the visibility interval is written once and the profile does not restate it).

The second half is not the first restated in different words. Peer visibility runs for thirty days past the end of the engagement that created it (R13), and for that window the viewer holds no active post anywhere — so the activeness half alone gave a manager whose term ended yesterday thirty days of the open default, which is the access this predicate exists to remove, on a delay. The first half is not the second restated either: two engagements both active at one venue are necessarily co-rostered there, but the view's `NOT EXISTS` ranges over **every** stint the person ever held at the venue, so a viewer bound only by co-rostering is handed a returning worker's older concurrency that the view withholds. Delete either disjunct and one test fails; both were measured.

**Residual, on the record and asserted:** the binding lapses with visibility, and `fetch_peer_profile/2`'s gate is visible **or** connected — so a pair who connected while co-rostered still reach each other's records after the tail, with no venue's rule applied. Deliberate: at that point no venue is *why* the viewer can see this worker, the connection is, and a connection exists only because the worker accepted it. The alternative — binding on "ever co-rostered at V" — never lapses and applies a venue's rule for life to somebody who left the trade. It costs the worker's acceptance plus the viewer's departure plus thirty days, by which time the viewer holds no employer session anywhere, and it has two remedies the suite asserts: one `set_disclosure/4` row, or `Peers.disconnect/2`, which closes the gate outright.

The gate on reading a peer's profile is **visible *or* connected** — `Peers.connected?/2` is U9's one addition to U8's context — because a connection outlives the visibility that produced it and a profile that vanished at the thirty-day mark would be taken from two people still in conversation. Declared entries reach a peer whole and carry no ledger at all: writing one is publishing it.

**`profiles_test.exs` is not sandboxed**, through `EngagementsFixtures.real_connections/0`, and here the reason is sharper than U5's: the thing under test is a view read through `EmployerRepo` over rows written through `Repo`, so under the sandbox every employer read would come back empty and every negative assertion in the file would pass for the wrong reason.

**Do not run `mix test --partitions N` alongside a plain `mix test` on this cluster.** `config/test.exs` interpolates `MIX_TEST_PARTITION` into the database name, so a partitioned run creates transient databases; their grants make `DROP ROLE employer_role` fail in `hospitality_coms_test`, and `PostgresRolesTest` then fails naming them. It is the same failure mode as migrating `hospitality_coms_dev`, arriving from a flag rather than from a command.

**An aborted run of any non-sandboxed file poisons the test database, and `EngagementsFixtures.purge/0` now says so.** A file that stops mid-way — `--max-failures`, an interrupt, an exception inside a fixture — has committed what it wrote and never reaches its `on_exit`; the next run then fails *inside the purge* on `ON DELETE RESTRICT`, across every file that takes real connections at once, with a stack trace pointing at cleanup. Two reviewers read that as a regression and bisected for it. `purge/0` rescues the violation and re-raises naming the residue and the fix, and confirms afterwards that no prefixed row survived. When it fires there is nothing to fix in the tree: drop, create and migrate `hospitality_coms_test` — **never `hospitality_coms_dev`**. Note also that `boundary_test.exs` asserts `Repo.all(Person) == []`, so committed residue fails it too, one file away from where the residue is.

## Data lifecycle

`retained_message_copies` and `retention_runs` in the person zone, created by `*_add_retention_columns.exs` along with `room_messages.delete_after`, `roster_entries.delete_after` and `venues.closed_at`. Everything is reached through `HospitalityComs.Lifecycle`, and `Lifecycle.Records` owns every query — writes and deletes included, so the context reaches zero query builders, which is `Profiles`' rule.

Issue #15 added a third operation, `reap/1`, and changed neither rule nor exemption — see **Authentication** for why the deleting half of a rate-limiting ticket landed here and why it is not two more triggers on `sweep/1`.

**`Lifecycle` is the only module permitted to delete (KTD21), with one enumerated exemption.** `lifecycle_test.exs` sweeps every module compiled from `lib/` out of the `imports` chunk — filtered on the compile-time source path, so the fixtures under `test/support` are not swept — and asserts the offender set is exactly `[Accounts]`.

**That sweep is blind to `repo.delete_all/1` inside a `Multi.run`, which is the idiom `Lifecycle` itself uses five times**, so the invisible form was the one a future author would copy from the one module the rule exists to isolate. Measured: the same delete written statically is caught and named; nested in a `Multi.run` it killed zero tests. A second sweep now parses each library module's source and flags any call to `delete`, `delete!` or `delete_all` on a repo alias, on `Multi`, or on a bare variable — `Map.delete/2` and `Process.delete/1` are aliases that are not repos — and asserts the offending *files* are exactly `lifecycle.ex` and `accounts.ex`. Its control parses three synthetic sources, one of each shape.

A third structural check pins `Profiles`' rule: `Lifecycle` reaches zero Ecto query builders and `Lifecycle.Records` reaches them. **Its known edge is shared with `peers_test.exs` and `profiles_test.exs` and is now measured**: a query with no interpolation and no dynamic composition expands entirely at compile time and calls into no builder, so it passes. One with a `^` anywhere does not, and every query in this tree takes an id or an instant. `Accounts` deletes `people_tokens` and nothing else: magic-link redemption claims the link, log-out ends the session, an email change expires every token. That is credential expiry rather than record destruction, and routing log-out through a module about retention would be worse than the carve-out. A second test bounds it by counting every base table across a log-out and asserting `people_tokens` is the only one that moved — **and an empty table compares zero to zero**, which made that bound vacuous over fourteen of the twenty-three base tables, both of U10's among them. Measured: four `Repo.delete_all` calls planted in `delete_person_session_token/1` produced twenty-eight passes and no failures. The fixture now writes one row in every base table `oban_peers` excepted, and asserts that emptiness set before it compares anything.

**It runs as the application's own role and never touches `EmployerRepo`.** Erasure crosses venues, which is what no employer session may do; and `employer_role` holds no privilege on any person-zone table and nothing at all on `room_messages`, so an employer connection could not perform either operation anyway. `grant_retention_zone` grants no `DELETE` to anybody, and `boundary_test.exs` still asserts the employer zone's inventory holds none.

### Erasure pseudonymises, and what it does *not* delete is the design

`erased_at` is stamped, `email` nulled and `display_name` overwritten with `erased_display_name/0` in one statement; `people_erased_email_removed` and `people_present_email_required` — U2's two check constraints — hold the address pair in opposition, which is why there is no `Person` changeset for it. The address must be *absent* afterwards and the name must be *replaced*, because a room keeps full history and a message with no author's name renders as nothing — two identifying columns, two remedies, one statement. See **Display names** for why only one of them has a CHECK holding it against `erased_at`. That opposition is the guarantee rather than the assertion beside it: measured, both `email: nil` removed *and* `email: "redacted@example.invalid"` fail **30 tests** with the same `Postgrex.Error`, so the column cannot be left populated whatever a context believes. Deleted: auth tokens, the erasing party's own peer messages, their declared entries, the disclosure rows that hand one of their own entries *over*, their retained copies, their scheduled Oban rows. Kept, each for its own reason:

- **`room_messages`, not one row written.** KTD15b put the display label on the engagement, so erasure reduces a number of rows proportional to *engagements*; `lifecycle_test.exs` compares the message rows field for field across an erasure as the control on that claim. KTD15c: bodies survive on a legitimate-interest basis and can still name people, so venue-room history holds personal data indefinitely.
- **`attested_entries`, also not one row written**, and it is the worker's portable record rather than a legitimate-interest carve-out. Nothing asserted this until a mutation found it: an `erase_person/1` that deleted every attested entry of the erased person's engagements passed lifecycle, profiles and revocation alike. Now compared field for field, in `room_messages`' shape.
- **`connection_requests`** — see **Peer graph**.
- **`attested_entry_disclosures` where `disclosed` is false, from both sides.** A `false` row *narrows* what an audience sees, so deleting one discloses **more** — and peer visibility runs thirty days past an engagement's end, so tidying it away would re-reveal exactly the entries the worker had hidden, at the moment they asked for erasure. Rows naming them as the *audience* belong to somebody else besides, whichever way those rows point.

  **A `true` row is the opposite and is deleted.** The old claim — "a disclosure row only ever narrows" — held for one of the two values, and the test wrote only that one. `Profiles.Records`'s peer rule reads a `true` row as an override beating the computed concurrency default, so keeping one leaves an erased person affirmatively disclosing an entry to a named peer for the whole tail with no session left to withdraw it. `lifecycle_test.exs` pins the split three ways: the `false` row survives, the `true` row goes, and a `true` row naming the erased person as *audience* survives.
- **`correction_requests`**, addressed to a venue, which is the other party — but R16 also serves one to any peer who can see the entry it contests, so it is not purely two-party: an erased person's own free text reaches third parties for the tail, while their declared entries, the same kind of self-authored text, are deleted. Deliberate: a correction request is an assertion *against* an attestation, and deleting the contest while keeping the attestation leaves the record worse for the erased person than leaving both.
- **`venue_room_suspensions`**, keyed on the engagement and naming no person. Listed because the enumerations above read as exhaustive and this was the table in neither.

**The thirty-day tail is a disclosure, not a defect.** A peer co-engaged with an erased person keeps seeing their attested entries — venue names, employer-authored role labels, dates — for thirty days after the last engagement ends. No email, no declared entries. That is identifier erasure applied consistently. **A second residue of the same tail**: they stay on a co-engaged peer's `list_visible_peers/1` for those thirty days, so a request can be sent to somebody with no session left to answer it, leaving a permanently current `connection_requests` row. Not closed here: visibility derives from engagements alone, and adding a `people` predicate to it is a U8 decision rather than a retention one.

**KTD17's exemption has a named state.** Erasing a venue's sole grant-holder succeeds, and `Lifecycle.orphaned_venues/1` is the list an operator re-seeds from: venues holding a live grant that no active engagement holds, derived rather than stored. A venue whose only grant was *revoked* is not on it — there is no authority to be the last holder of, which is a venue that was wound up — and `EmployerGrant.live_at/2`'s predicate is reused so "live" cannot mean two things. A venue that was **closed** is not on it either, and for the same reason by another route: `close_venue/2` starts a retention clock and revokes nobody, so a wound-up venue satisfied every other clause and was handed to an operator as something to re-seed.

Open terms close at `GREATEST(starts_at, now)`, which is `end_engagement/2`'s widening reached from the other side: a not-yet-started engagement closes at its own opening, the empty range, so the person's dates are free rather than reserved for a term nobody will work. `lock_version` is incremented so a renewal in flight loses.

### Retention reads stamped columns and joins nothing

Four triggers, and **no join to the period a deadline came from**. That is the single most important decision in the unit: computing at sweep time lets a backdated engagement end move a deadline into the past and have the next unattended run destroy a worker's messages. Two tests stamp a deadline, then move the period into the distant past with a raw `update_all`, then sweep between the two and assert the rows survive.

| Trigger | Column | Stamped when | Window |
|---|---|---|---|
| own-message copies | `retained_message_copies.delete_after` | **the term closing**, null until then | 90 days past the engagement's end |
| shift messages | `room_messages.delete_after` | the message is inserted | 30 days past `shift_rooms.closes_at` |
| shift roster | `roster_entries.delete_after` | the entry is inserted | the same instant |
| venue-room history | `room_messages.delete_after` | **venue closure**, null until then | 30 days past it |
| engagements, attested entries | — | never | never |

**Two of the four are null until an event happens and it means the same thing in both**: no clock yet, because the event that starts it has not occurred. For the archive that event is the term closing, which is the state after which `ends_at` can no longer move — `renew_engagement/3` answers on activeness and `end_engagement/2` on "has not closed" — so the stamp is written exactly once from a value that can never be revised. `retained_message_copies.delete_after` is nullable for that reason, and `retained_message_copies_deadline_after_sending` spells the `IS NULL` disjunct out rather than relying on a CHECK being satisfied by null.

**Thirty against ninety is load-bearing, and it took a second test to make that true.** It is what makes KTD16's argument for physically separate rows observable: the venue's copy of a shift message dies at thirty days while the worker's copy of the same words lives to ninety. The test that claimed it swept just past the *shift's* deadline, and the two deadlines hang off different origins — so it was satisfied by the engagement being longer than the shift, and `@own_copy_retention_days` mutated from ninety to **two** killed nothing. The pair that replaces it sweeps at `ends_at + 89 days` and `ends_at + 90 days + 1s`, both long past the shift's, with the venue's copy already gone at each: 90 → 30, → 2 and → 200 each kill exactly it.

`Lifecycle.close_venue/2` stamps **only** the deadlines that are still null, so a shift message's fixed deadline is never overwritten by the venue's clock. It takes no `EmployerScope` and is on no transport: `employer_role` holds nothing on `room_messages`, and closing a venue destroys, on a clock, the conversation history of everybody who ever worked there.

**Closing a venue also shuts its room.** `Rooms.send_venue_room_message/3` answers `:room_closed` once `closed_at` is set, and resolves the venue under `FOR SHARE` inside the transaction that writes the message. Without both halves the sentence above was false: closure stamps the rows that exist when it runs and then refuses to run again, and `delete_after < instant` never matches a null — so every message written from the closure instant onward, and every message racing the closure, was retained for ever. Reading a closed venue's room is untouched; a clock is what closure puts on history, not a wall.

Half-open, `delete_after < instant`: a row whose deadline is exactly the sweep's instant survives.

**The archive is taken in the transaction that writes the message, and dated by the expiry announcement.** KTD16 says "inside the engagement-end transaction"; that transaction is an `EmployerRepo.scoped_transaction/2` and `employer_role` holds no privilege in the person zone, so it structurally cannot write the copy. Writing it when the expiry was *announced* was the first answer and **it lost data**: a copy cannot be taken later than the instant its source may be deleted, a shift message's source dies at `closes_at + 30 days`, and every ordinary term outlives its shifts by months — so the venue's copy was swept before the announcement fired and the worker's copy was never created. That is KTD16's named failure ("a person whose engagement ended long after a shift would lose their own copy on the shift's clock") arriving through the trigger rather than through the schema, and the fixture was arranged so no test could see it.

So `Rooms` calls `Lifecycle.retain_message/3` inside the send's `Ecto.Multi`, on both room kinds — one transaction through one repo, which is closer to KTD16's ask than the announcement ever was. `Workers.ExpireEngagement` still calls `retain_own_messages/2`, which is now the *backstop*: it stamps the deadline once (`is_nil(delete_after)` is the whole condition) and copies anything with no copy — words written before U10, or a copy whose own transaction rolled back. A lost announcement therefore leaves an archive with **no deadline**, which over-retains rather than losing anything.

That backfill is chunked at 500 rows. `insert_all` binds one parameter per field per row and Postgres refuses more than 65535, so ten fields put the wall at 6553 messages — an ordinary year at a busy venue — past which the statement raised `Postgrex.QueryError` out of `perform/1`, which has no rescue and whose call site matches on `{:ok, _}`. `retention_sweeper_test.exs` drives 6600.

**Suppression for an erased person is derived, not stored, and it is taken under `FOR SHARE`.** `retain_own_messages/2` and `retain_message/3` both resolve `people` with `erased_at IS NULL` and `FOR SHARE`, which conflicts with the `FOR UPDATE` `erase_person/1` opens with. Unlocked they were two unsynchronised statements: an erasure committing between the check and the insert left copies its own `delete_all` had already run past, and nothing blocked, because the copy's foreign key takes `FOR KEY SHARE`. Erasure also deletes copies that already existed, so the invariant is "no retained copy of an erased person exists or will exist" rather than a prospective rule.

**`source_message_id` is deliberately not a foreign key.** `ON DELETE RESTRICT` would make the shift-history sweep fail the moment a copy outlived its original; `ON DELETE CASCADE` would delete the archive on the venue's clock. It is **not** because a person-zone key into the employer zone would be a second crossing — that reason was stated in four places and is wrong. KTD2's single crossing is about naming a *person*; arrows point into the employer zone freely, and `attested_entry_disclosures.audience_venue_id` is already such a key and is documented as deliberate. Ownership is still a database rule — `(engagement_id, person_id)` MATCH FULL into `engagements (id, person_id)`, reusing the index `create_profiles` built for `attested_entry_disclosures`, which is why `add_retention_columns` has to be rolled down **before** `create_profiles` and is the outermost layer of `boundary_test.exs`'s rollback nest. Only the *first* of that nest's two dependencies is loud: `create_profiles`' `down` meets `RESTRICT` and raises naming `retained_message_copies`, which is now asserted; rolling `create_roster_entries` down underneath drops `delete_after` with the table and raises nothing.

**`down` restores the schema and loses two things**, and on an empty database that is invisible. `retained_message_copies` comes back empty — where the shift sweep already took the source rows the words are gone from both tables — and `venues.closed_at` comes back empty, so a closed venue reverts to trading and its messages to a null deadline. A rollback therefore silently extends retention indefinitely. The migration's moduledoc carries the capture SQL; `boundary_test.exs` asserts both losses against seeded rows, which is also the only place the migration's `UPDATE … FROM shift_rooms` backfill and its `SET NOT NULL` are proved on more than zero rows.

**`roster_entries.delete_after` is `NOT NULL` with no default, which makes this migration deploy-before-migrate.** Code that predates U10 writes a null and is refused. The three-phase alternative buys a rolling-deploy window and costs two migrations and a period where the column means nothing; it is the right shape at scale and is deliberately not taken here.

**`batch_size` and `ceiling` are a pair, not two settings.** Four triggers times 500 is 2000, and the ceiling is 5000 — deliberately out of reach of a correct run, because it is the guard that fires when a batch bound is missing or a later trigger is added without one. A ceiling an ordinary run could hit would refuse the same rows on every tick and the sweep would never progress again. Above it, **every** trigger rolls back, not only the one that overflowed.

Every run writes a `retention_runs` row carrying the instant the sweep *used* — not the instant the row was written, which differs whenever the clock is injected — and four counts rather than a total. On the ordinary path the record is written inside the deleting transaction, so a committed deletion is never unrecorded; on the refusal path it is written after the rollback, because that is the case a record matters most for.

**Two more test files are not sandboxed:** `lifecycle_test.exs` and `workers/retention_sweeper_test.exs`, for U5's reason. `EngagementsFixtures.purge/0` grew two deletes and one correction that is easy to miss: **an erased person has no email**, so every prefix-based lookup in that file had to learn to find them by `erased_at` as well, or a lifecycle test's people would survive every purge invisibly.

## Realtime

Two sockets, declared in `HospitalityComsWeb.Endpoint` with `auth_token: true` so the session token arrives on the `Sec-WebSocket-Protocol` header instead of a query parameter that lands in access logs. It reaches `connect/3` as `connect_info[:auth_token]`.

**`PersonSocket` routes `venue_room:*`, `shift_room:*`, `peer:*` and `profile:*`. `EmployerSocket` routes `employer_venue:*` and nothing else** (KTD9). The absences are the design: no peer topic, so an employer session's join is refused in Phoenix's dispatch with no application code running; no room topic, because room conversation is worker-facing and `employer_role` holds nothing on `room_messages`; no profile topic, because a profile is person-zone data and the disclosure ledger is the list of what a worker chose to conceal — an employer-facing one would tell a venue which of its workers is concealing something, which discloses strictly more than the entries do. Adding a route to `EmployerSocket` is a boundary change, not a feature. `sockets_test.exs` asserts against `__channel__/1` — the table itself — with the person socket's matching entry as the control, so an empty table cannot pass it.

**`check_origin` is explicit for production and a boot raises without it.** `WEBSOCKET_ORIGINS` is a comma-separated allowlist, handled exactly as `MAGIC_LINK_BASE_URL` is and for the same reason: Phoenix's default of `true` checks `Origin` against the endpoint's `:url` host, so a browser client served from anywhere else has its upgrade refused *before* `connect/3` runs, with nothing in this application's logs to say why. A value naming no origin is refused too — `check_origin: []` refuses everything, which is the same silent failure by another route.

**`id/1` is the session, never the person** (KTD7): `HospitalityComsWeb.PersonAuth.session_topic/1` of the token's digest, which is the exact string `disconnect_sessions/1` already broadcasts `"disconnect"` to. Both sockets return the same string for the same token, so logging out drops both transports of that session and neither transport of any other. There is one spelling of it; two that drifted would make log-out a silent no-op against an open socket.

**Connect authenticates; join re-authenticates *and* authorises.** Nothing is cached on a socket except the person's **id** and the session token's **digest** — no `Person` struct, because a channel crash report is `inspect/1` of the socket, and no raw token, because U2 hashes session tokens at rest so that a leak yields digests.

`join/3` asks two questions again, every time. `ChannelAuth.join_scope/1` re-derives the session from the digest against the same `people_tokens` row and the same fourteen-day horizon an HTTP request is checked against; then `Rooms.fetch_venue_room_membership/2`, `Rooms.fetch_shift_room_reader/2` or `Engagements.fetch_grant_holding_engagement/2` re-derives the authority. Together they are what makes the *refused rejoin* the revocation (KTD8). `revocation_test.exs` asserts that rejoin without looking at the channel process at all: deleting the `{:stop, …}` leaves it passing, deleting the re-derivation is what makes it fail. Both measured.

The session is re-derived **per join, not per event** — deliberately, with the residue written out in `ChannelAuth`'s moduledoc. Authorization *is* per event.

**The instant is per inbound event, not per join** (KTD5). `ChannelAuth.person_scope/1` reads the clock at the top of every `handle_in/3`, and `join_scope/1` does the same for a join. A channel joined at 22:00 has its 23:31 send refused by a room that closed at 23:30, on the same process, with no rejoin and no job.

**A topic suffix is user input.** `ChannelAuth.topic_id/1` is the only way one becomes an id: `byte_size(id) == 36` and then `Ecto.UUID.cast/1`, which is `EmployerScope.uuid!/1`'s shape without the raise. The byte size is load-bearing rather than a pre-filter — `cast/1` alone accepts sixteen raw bytes and encodes them. A malformed suffix gets the same sentence an id that names nothing gets (AE1); before this it raised `Ecto.Query.CastError` out of `join/3`.

**Every channel answers what it does not know.** `Phoenix.Channel.Server` dispatches to `handle_in/3` unconditionally, so all four carry a terminal clause returning the `bad_request` envelope. Both room channels carry a catch-all `handle_info/2`: the engagement topic is shared by every channel that engagement opened, so an unmatched message there crashes the venue room *and* every shift room at once.

There is no separate employer credential. An employer session is a person session plus a venue on the channel topic; `Engagements.fetch_grant_holding_engagement/2` resolves the engagement at that venue holding a grant the venue has not revoked, and `ChannelAuth.employer_scope/2` turns it into an `EmployerScope`. **`ChannelAuth.employer_scope/2` is now a delegation**: it derives the session from the token digest, which is the socket-shaped half, and hands the rest to `HospitalityComsWeb.EmployerAuth.employer_scope/2`, which is `(PersonScope, venue_id) -> {:ok, EmployerScope} | {:error, :no_grant}` and knows about no transport at all. Same signature, same behaviour, same `:no_session` arm; `employer_venue_channel_test.exs` is the regression proof and its assertions did not change. **Whoever puts the profile on the transport must call it per event and must not read `socket.assigns.grant_id`**, which is written once at join and never refreshed. U9 added no transport surface — its issue names contexts, migrations and one test file, and its verification is a context-level claim — so `EmployerVenueChannel` is still where an employer profile event would go, and `PeerChannel` where a peer one would.

`HospitalityComs.PubSub` is both the module and the registered name of the PubSub server. `subscribe(scope, target)` keys on the scope struct and pins the id where the scope carries one — an employer scope handed a peer topic, or a person scope handed another person's, is a `FunctionClauseError` before a registration exists. **It is not the only way a process becomes a subscriber** (`Phoenix.Channel.Server` subscribes every joined channel to its own topic), and **it gates three of its five targets not at all**: `{:venue_room, _}`, `{:shift_room, _}` and `{:engagement, _}` accept any id from any person scope, authorized by the caller that resolved it and by nothing here. Read those clauses as a type check, never as an access check — `subscribe` issues no query, so no privilege and no RLS policy would notice. `{:engagement, id}` resolves through `Engagements.topic/1`: U5's after-commit broadcast, not a second mechanism.

**Suspension nudges the channels it closes.** `Rooms.suspend_venue_room/2` broadcasts `{:venue_room_suspended, …}` on the engagement's topic after the write and only if it happened, best effort and logged. `VenueRoomChannel` pushes `"access_suspended"` and stops with `{:shutdown, :suspended}`; `ShiftRoomChannel` ignores it in a clause of its own, because KTD18 confines suspension to the venue room and the nudge only reaches shift rooms because one engagement opens both.

**Presence is keyed on `engagement_id`, never `person_id`** (KTD15b), and lives only on person-socket topics. That is what stops it becoming the arithmetic U6 closed: a suspended person is absent from presence and still on the room's roll, and no employer surface can reach the diffs. There is no `untrack` call anywhere; the tracker monitors the channel process, and `presence_test.exs` proves it by killing a channel outright and watching the leave arrive. Three residues are recorded in `HospitalityComsWeb.Presence` — a manager is also a worker and can watch the diffs over time, metas stamp `role_label` at join and never refresh, and `Phoenix.Tracker`'s twenty-minute `:permdown_period` keeps a partitioned node's presences listed.

`max_channels_per_transport` is at Phoenix's default of 100, and **KTD10's argument for that number is wrong**: multiplexing is worker-side, `EmployerVenueChannel` is one channel per venue with none, and the person socket's readable shift-room set is unbounded and grows with every shift ever rostered. Clients must open shift rooms on demand rather than joining the list. At the limit Phoenix answers `%{reason: "too many channels joined"}` — **not an `ErrorEnvelope`**. The real bound and who can exceed it are written out in `endpoint.ex`.

**`PeerChannel` is the multiplexing point U7 left empty, and U8 filled it.** Nine events, a clause answering the six that need an id and did not get one, and a terminal clause; every event names its conversation in the payload and none in the topic, so conversations are not part of the channel count and no per-conversation topic name exists for a later unit to copy into an employer socket's table. `join/3` authorises nothing beyond the session and the topic naming that session's own person — there is no membership behind a peer topic — so **every event authorises itself in the context**, which is the only shape that works when one channel carries conversations with different people opened and closed at different times. The instant is per event as everywhere else: `peer_channel_test.exs` disconnects a conversation *after* the channel joined and watches the next send refused.

**The topic is `peer:<person_id>` and the suffix is checked at join.** It was the bare string `"peer"`, which put every person's peer channel in the cluster into one Phoenix group — `Phoenix.Channel.Server` subscribes each joined channel to its own topic — so a `broadcast/3` from that file would have delivered every conversation to everybody, guarded by a comment saying not to. The suffix removes the group: `admitted/3` matches it against the joining scope's own person id with a repeated variable, and the resulting topic is exactly `PubSub.topic({:peer, person_id})`, which is where `Peers` publishes. That coincidence is also why `join/3` subscribes to nothing — Phoenix has already subscribed the channel to the topic the announcements arrive on, and a second `PubSub.subscribe/2` would deliver every notice twice. `peer_channel_test.exs` pins single delivery with a `refute_push` behind the `assert_push`.

A disconnect **does not stop** the channel, unlike a room revocation — the topic is the person, not the conversation, and stopping would take down every other conversation on it.

**Rendered peer shapes name entities `<entity>_id`.** `rendered_message/1` said `id` in the send reply and the history while the live `peer_message` push said `message_id`, so one entity had two key names on one channel; it is `message_id` everywhere now.

**And since #73 every one of the four names a person by name as well as by id.** `rendered_conversation/1` carries `peer_display_name`, `rendered_request/1` carries `requester_display_name` and `addressee_display_name`, `rendered_message/1` carries `author_display_name` — the same key `RoomChannel.rendered/1` uses, because a message's author is one entity whichever room or conversation carried the words. Three of the four rendered a bare uuid before and the client rendered `shortId(…)` of it. **Both** request names rather than one viewer-relative counterpart, because that function serves four call sites and takes no viewer; a counterpart's name would make one entity's shape depend on who asked. Every render heads on `is_binary(name)`, so a read path that forgot the join crashes rather than shipping a `null`. The **four notices are unchanged** — `use-peer-surface.ts` re-asks the affected list on each of them and applies only `peer_message` directly, so that one carries the name and a name on the other four would be a field nothing reads; `peer_channel_test.exs` already pins the push's whole key set against the send reply's, which is what makes that non-optional.

**The instant beside it had the same defect and survived that fix** (#31). The push went through `stamped/1`, which is generic over all five `handle_info` notices and writes `at`, while the reply and the history wrote `sent_at`. The push now goes through `sent/1` — which calls `stamped/1` and renames the one key — and **the other four still say `at` on purpose**: `at` means "when this notice happened", and a request, a decline, a connection and a disconnection are events whose instant is the event's, none of which was *sent*. Renaming `stamped/1` instead would have been the wrong fix and would have passed every assertion in the file, so `peer_channel_test.exs` carries a test that reads the instant key of all five. U12's client had two decoders, each refusing the other's key; it is one now. `rendered_request/1` carries `accepted_at` and `declined_at` alongside `state`, because `state` is the claim and those are when it became true. `peer_channel_test.exs` asserts the exact key sets, since nothing else pins them and U12 is written against them.

**`ProfileChannel` is U9's contexts reaching a browser, and it carries no server pushes** (#70). Seven events on `profile:<person_id>` — `profile`, `list_disclosures`, `set_disclosure`, `declare_entry`, `amend_declared_entry`, `request_correction`, `peer_profile` — each one exported function of `HospitalityComs.Profiles`, which did not change, and each one rendered by a function next to the channel.

**#73 added an eighth, and it is the only one that does not call `Profiles`.** `list_audiences` takes `%{}` and answers `%{venues: [%{venue_id, name}], people: [%{person_id, display_name}]}`, which are the two kinds `Disclosure.audience/0` has — without it the disclosure control made the worker type a raw uuid. One event rather than two, so both halves are answered at one instant; `PeerChannel`'s `list_requests` is the same shape. The two relations belong to other contexts — *where do you work* is `Engagements` and *who can see you* is `Peers` — and a `Profiles.list_audiences/1` composing them would have to answer an Ecto schema, which #36 forbids that context, or invent a third spelling of a venue inside it. So this is the first channel in the tree to call two contexts, which every controller already does. `venue_id`/`name` rather than `venue_id`/`venue_name`, because a venue listed **as itself** is spelled that way by `EmployerController.render_venue/1` and `RoomController.render_venue_room/1` and both client decoders read it; `venue_name` is what a venue named *inside another entity* is called.

**`Engagements.list_engaged_venues/1` is the venue half and is neither of the two lists that already existed.** It is `list_managed_venues/1` with the grant filter dropped — where somebody *works*, where that one is where somebody may *act* — and the predicate is the employer view's own: `employer_visible_attested_entries` resolves a worker through `viewer.starts_at <= now AND viewer.ends_at > now`, so a venue is offered as an audience exactly while it can read the record. Not `Rooms.list_venue_rooms/1`, which subtracts suspensions (KTD18) and would take a suspended worker's own venue out of their own picker; not `VisibleEntry.venue_id`, which is the venue that *asserted* an entry rather than one that could be an audience for it, and is why the picker could not be built before. **Residue, on the record:** a venue whose term has ended is not offered, because it cannot read the record either; a decision already taken about it stays in the ledger and applies again if the worker returns. **A second one, measured:** the deduplication both venue reads claim is unreachable — `engagements_no_overlap` refuses a second engagement for one person at one venue over an overlapping term, so two active ones cannot exist and the set membership is belt to that brace. `client/src/features/profile/contract.ts` is the specification rather than a description of one: U12 built the surface ahead of the transport on purpose, wrote the envelope down in that file, and its decoders **refuse `id`** for the three entities whose Ecto schemas spell it that way — so a channel putting a schema on the wire produces a surface that renders empty and says nothing, which on this surface is also a claim about somebody's working life.

**It is request/reply with a join lifecycle, which is HTTP's shape, and that is written into the moduledoc rather than glossed.** `Profiles` broadcasts nothing and `use-profile-surface.ts` registers zero push handlers. Two things make it a channel anyway: the client is already written and tested against exactly this contract, and **the rooms surface's reason for going HTTP does not transfer** — `RoomController` exists because two of its four reads are lists you need *before* you have a room to ask through, while a profile topic is keyed on the session's own person id, which the client already holds. The three announcements that would justify it staying a channel are named in the file: an employer attesting an entry, a correction being resolved, and a disclosure decided on another device. Each is one broadcast away, and the day one exists it wants a `Profiles.topic/1` beside `Peers.topic/1`.

**The suffix is the person and the check is `PeerChannel`'s repeated variable**, for a sharper version of its reason: a peer topic leaks a conversation and this one leaks every term somebody has served plus the ledger, which is the list of what they chose to conceal. The join reply is `%{person_id, incompleteness_notice}` and **it is the only reply that carries a notice** — `incompleteness_notice/0` is arity zero so it cannot become an oracle, and arriving once on the join is what makes that structural, since a join is about the session and no profile read can influence one. Both profile replies are pinned by exact key sets for that reason: a `hidden_count` is a field being *added*, and an exact key set is the only shape that fails in that direction.

**Four codes, which is `refusal-message.ts`'s whole vocabulary, and one deliberate bend.** `unauthorized` join-only; `not_found` for every id that resolves to nothing this person owns, malformed and unknown alike through `ChannelAuth.topic_id/1`; `bad_request` for an event with no clause and a payload missing what the event needs; `unprocessable_entity` for a changeset, with `fields`. Worker-authored text is deliberately **not** pre-checked, so a blank label or body comes back naming the input the worker filled in. The bend is that **`audience_kind` and `audience_id` are one value spelled as two fields**, so a pair that is not an audience is `bad_request` rather than `not_found`: they are a tagged union rather than a key, both halves are input from the caller's own browser, and the `not_found` copy for that event reads "That entry is not one of yours", which is a lie about a mistyped venue id. Nothing is enumerable through it — an audience that is an id and names no venue is already a foreign-key changeset error by the context's design.

**The worker's own record is not ledger-filtered and the test for it needs its control.** `list_attested_entries/1` is explicit that disclosure governs what *others* see; the disclosure controls are rendered per entry, so an entry that vanished when it was hidden could never be un-hidden. "The concealed entry is in the reply" passes against a `set_disclosure` that wrote nothing, so `profile_channel_test.exs` reads the same entry through the *employer's* door at the same instant and requires it to be absent — different reader, different repo, opposite answer. `peer_profile` is gated **visible or connected** in the context and gets no second gate here, with a connected pair whose visibility has lapsed as the test and a stranger beside it as the control.

**Nothing in the channel validates what a changeset validates.** `DeclaredEntry`'s `cast/3` allowlist is exactly the four fields the contract sends, `CorrectionRequest`'s is `[:body]`, and `Disclosure` casts nothing at all, so the payload goes straight to the context — the opposite call from `EmployerController`'s `@term_fields`, where the changeset *would* cast the dangerous field.

**The `handle_info/2` catch-all kills nothing today and is kept anyway, measured rather than asserted.** It is the only `handle_info/2` clause on the channel, so deleting it makes the module export none, which restores exactly the Phoenix warn-and-ignore fallback it stands in for — 0 kills. Add one specific clause *and* delete it, which is the state the day an announcement arrives, and the stray-message test fails. Same shape as #65's `is_binary(label)` pair: neither number says anything alone.

**One assertion in that file is a control in a different shape from all the others**, and it is the only one that could catch what #70's reported symptom actually was: `assert_reply` hands back the Elixir term, so a reply carrying a bare `%VisibleEntry{}` satisfies every key-set assertion and raises `Protocol.UndefinedError` in the serializer the first time a browser asks. One test puts the join reply, the profile reply and the ledger through `Jason` and asserts the **string** keys and **string** enum values the client narrows against. Measured: replying with the structs rather than the rendered maps kills that test and nothing else.

**Not one line of the surface changed**, which is the whole claim for a contract written ahead of its implementation. The channel was built *from* `contract.ts` and is tested against its payloads; where the two disagree the file is right. `contract.ts`'s banner and three passages in `client/README.md` did have to change, because they said no channel answered these events and that stopped being true — prose rather than shapes, and the distinction is the rule: an edit to a *shape* under `client/` is the tell that the channel has diverged, an edit to a sentence that has become false is maintenance.

**Eight more test files are not sandboxed**, through `HospitalityComsWeb.ChannelCase`: `sockets_test.exs`, `presence_test.exs`, `revocation_test.exs`, `venue_room_channel_test.exs`, `shift_room_channel_test.exs`, `peer_channel_test.exs`, `profile_channel_test.exs` and `employer_venue_channel_test.exs`. It takes real connections like `EngagementsFixtures.real_connections/0`, then makes ownership `{:shared, self()}` because a channel runs in a process of its own with no connection checked out, and pins `Clock.Offset` to the fixtures' instant because a channel reads the clock. Getting the shared ownership wrong does not look like a failure — it looks like `DBConnection.OwnershipError` inside `join/3`, which the channel reports as a crash, which reads like the join being refused.

## Employer transport

Nine routes, `HospitalityComsWeb.EmployerController`, all on the existing `:authenticated_person` pipeline.

```
GET    /api/employer/venues                        the venues this session may act for
GET    .../venues/:id/engagements                  that venue's people, now
POST   .../venues/:id/invitations                  an offer, and the code that redeems it
GET    .../venues/:id/shift-types                  the kinds of shift this venue runs
POST   .../venues/:id/shift-rooms                  tonight's shift
GET    .../venues/:id/shift-rooms[?extent=all]     the venue's shifts, most recent first
POST   .../shift-rooms/:id/roster                  put an engagement on one
GET    .../shift-rooms/:id/roster                  who is on it now
DELETE .../shift-rooms/:id/roster/:engagement_id   take them off it
```

**There is no employer pipeline and there must not be one.** Authority is per venue and the venue is a path parameter, so a pipeline would have to know which venue before the router had parsed one. `EmployerAuth.employer_scope/2` is called inside each action that names one, and resolves the acting grant against the database on every request.

**`HospitalityComsWeb.PersonAuth` authenticates and `HospitalityComsWeb.EmployerAuth` authorises.** Two conn-side modules whose names both end in `Auth` is a trap, so both moduledocs say which is which in their first paragraph. `EmployerAuth` never looks at a token, a header or a connection; it takes a `PersonScope` and a venue id, and takes its instant off the scope `PersonAuth.fetch_person_scope/2` already built. It is therefore **absent from `.credo.exs`'s `:boundary_modules`**, and an entry appearing there would be the tell that it started reading a clock of its own.

**The refusal is `404` here and `unauthorized` on the channel, deliberately.** `fetch_grant_holding_engagement/2` answers `:no_grant` identically for an ended engagement, an engagement holding nothing, a revoked grant and a venue that does not exist; R17 requires the wire to preserve that, and a `403` would confirm the venue exists. A channel join has no resource to be not-found about and `EmployerVenueChannel` is internally consistent, answering `unauthorized` for a nonexistent venue too. Two transports, one refusal boundary, two status vocabularies — recorded so it is not read as drift.

**`Engagements.list_managed_venues/1` is the picker's read, and it is *not* `Rooms.list_venue_rooms/1`.** That list already returns `{venue_id, name}` for every venue a person is engaged at and looks free, but it subtracts suspensions and employer authority never does (KTD18). So a manager who used the person-side venue-room opt-out would keep full authority over the venue and vanish from their own picker, with no other way in and nothing failing anywhere to say so. The new read composes `active_at/2` and a live-grant subquery and no suspension filter; `engagements_test.exs` pins the suspended manager appearing here **with `list_venue_rooms/1` answering `[]` beside it**, because without that control a suspension that silently did nothing satisfies the test.

`EmployerGrant.live_at/1` is the venue-free half of `live_at/2`, which is now composed from it — the picker asks about every venue at once and has none to pass in, and a second spelling of "live" is the thing `Records.decision_set/4`'s own docstring forbids. **`Lifecycle.Records.live_grant/1` and `live_grant_holder/1` restate the predicate inline anyway**, correlated on `parent_as(:venue)`, while `orphaned_venues/1`'s docstring claims they reuse it. That claim is false today; it is left alone rather than fixed, because composing into a correlated subquery changes a retention query's plan for no assertion.

**Rendered shapes are field lists and their key sets are pinned against literals.** An engagement is `{engagement_id, role_label, starts_at, ends_at}` and a venue is `{venue_id, name}` — the same `venue_id`/`name` spelling `RoomController.render_venue_room/1` uses, because one entity gets one key name across this API. Three pins, each catching what the others cannot: a structural `@spec` naming every key (Dialyzer), an exact key-set equality against a literal in the test (fails when a field is *added*, which is the direction `person_id` arrives from), and a control asserting `Engagement.__schema__(:fields)` still contains `:person_id` so an empty render cannot pass for a redacted one. Every list is additionally asserted **non-empty before anything is asserted about it**.

**R16's route-level test cannot fail for the mechanism this unit built, and that is measured rather than argued.** Every employer context call opens with `Venues.fetch_acting_grant/1`, which resolves the grant live-at-instant inside the transaction — so revoking a grant between two requests and asserting the second is refused stays green with `EmployerAuth` handing over a stale grant id. The assertion that carries R16 is against `EmployerAuth.employer_scope/2` **directly**; the route-level one is labelled end-to-end coverage in the test file, and the label must not drift.

**`employer_controller_test.exs` is not sandboxed**, and here it is mandatory rather than stylistic: an employer surface reads through `EmployerRepo` and the bridge is written through `Repo`, so under the sandbox every list comes back empty and every negative assertion in the file passes for the wrong reason.

**One thing that reads as coverage here and is not.** The sixteen-raw-bytes id is in the refusal test as input-class coverage and is **not** evidence for `EntityId.cast/1`'s `byte_size(id) == 36`, measured: dropping that guard kills nothing in this file. Both branches converge on one flat `404`, which is R17 working. The guard is observable on `GET /api/venues/:venue_id/shift-rooms`, which answers `200 []` for a castable unknown id, and `room_controller_test.exs` is where it is pinned. What the *malformed* id proves here is that the cast happens at all — without it the resolver raises `Ecto.Query.CastError` and Phoenix answers `500`.

## The handshake over HTTP

U2's two write routes, and they are the two halves of the gesture the whole employer surface exists to show.

```
POST /api/employer/venues/:venue_id/invitations   an offer, and the code that redeems it
POST /api/claims                                  the worker accepting it, in their own session
```

**`POST /api/claims` is not under `/employer` and must not be.** A claimant needs no grant, no engagement and no prior relationship to the venue — the code is the whole of what they hold. `claim_invitation/2` casts nothing else: accepting an offer is accepting *the* offer, so the term, the role and the venue all come off the invitation and a claim cannot grant itself a year at a venue that offered a fortnight.

**The claim's failure is `Ecto.Multi`'s four-tuple and a two-element clause matches none of it.** `{:error, step, reason, changes}`, where the reason is an atom for `:consume` and `:conferrable` and a changeset for the three write steps. A `{:error, reason}` clause compiles, passes every test that never reaches a refusal, and turns the first refusal in front of an audience into a `FunctionClauseError` rendered as `500`.

**The claim's three code refusals are deliberately distinguishable, and this is the only place in the API that is not flat.** R6, and it discloses nothing: the holder of a code already holds it, so "there is an offer behind this" is not news and "it was taken" and "it lapsed" are facts about their own offer. `ErrorEnvelope`'s `code` **is** the status atom, so distinguishable by a machine and a distinct status are one sentence here — `404` unknown, `409` already claimed, `410` expired. `:grant_not_live` shares `409` with its own sentence, being a different family: the code is fine and **unspent**, and re-issuing the grant makes it good again. Do not sweep these into consistency with `EmployerController`'s one flat `404`; the argument is in `ClaimController`'s moduledoc so that nobody has to.

**The offer route casts exactly four fields off the body and `grant_id` is not one of them.** An invitation carrying a grant is an invitation to *manage*, and widening that `Map.take/2` is how a form that hires a worker comes to mint a manager. The consequence is that `issue_invitation/2`'s `:grant_not_live` arm is **unreachable from that route** and handled anyway; it is carried untested and `EmployerController`'s moduledoc says so. The *claim* route's matching arm **is** reachable — a conferring offer is issued through the context and its grant revoked before the code is presented — and is tested. The plan said neither was; one of them is.

**KTD-E5's three defaults are `scope.now`, `+90 days` and `+7 days`, and the seven and the fourteen are independent constants** (issue #42). The default is not derived from `Invitation.max_code_validity_in_days/0`; the only relationship asserted between them is a test, that the default lands strictly inside the bound. `starts_at` is *now* rather than any later instant because `list_engagements/1` is active-at-instant, so a term opening tomorrow produces an engagement the issuing manager's own people list does not show — which in a demo reads as the claim having failed, and is what the F1 end-to-end test catches.

**The fourteen-day bound is declared twice with the same message, so no route-level test can attribute a refusal to either.** `Invitation.validate_code_validity/2` and the `invitations_code_expiry_within_bound` CHECK both refuse, and `declare_constraints/1` gives the CHECK the changeset's exact wording — measured: neutering the changeset half kills nothing at the transport. That is a redundant pair on purpose (the CHECK covers a `Repo.insert_all` that never met a changeset) rather than one to delete. What the controller test does pin is the bound *and the number in its message*, so moving `@max_code_validity_in_days` without moving the migration's literal fails there as well as in `constant_agreement_test.exs`.

**Two fixture designs are the substance of U2, and one of them is not what the plan said.** Both AE2 and AE3 need **two claimants**, because every offer these tests issue carries the same venue and the same defaulted term, so a second engagement for one person collides on `engagements_no_overlap` before anything under test is reached. AE2's one-claimant version fails against a *correct* tree with `422` naming `period`. AE3's is subtler: the plan claims the count reaches 2 without the consume guard, and **it does not — measured, it stays at 1 with two claimants as much as with one**, because `engagements.invitation_id` is uniquely indexed. So AE3's count certifies nothing either way and its **status** is what carries it; two claimants are still the right fixture, on the weaker claim that they remove one of three mechanisms that would otherwise all refuse the same call.

**`claim_code` needs no entry in `filter_parameters` and adding one is the bug.** The list is an allowlist since issue #53, so the code is redacted for not being named; `claim_controller_test.exs` pins it over a real request with a code that demonstrably worked, with the dispatch line asserted present and `venue_id` asserted verbatim beside it — both mandatory, because an absence assertion passes against a log that captured nothing and `config/test.exs` makes the empty capture the default.

**The rate limiter is still `POST /api/log-in`'s alone, now that this surface writes.** Both new routes need a live session; the offer route needs a live grant resolved against the database as well, and sends no mail. What it can be abused for is fan-out — unbounded outstanding offers at one's own venue — which is the shape already filed under issue #15 alongside peer requests, and wants one answer for the API rather than a counter on one action.

**`claim_controller_test.exs` is not sandboxed**, for `employer_controller_test.exs`'s reason and one sharper: a claim reads an invitation written through `EmployerRepo` and writes an engagement through `Repo`, so under the sandbox every claim in the file would fail on a foreign key.

## Shifts and the roster over HTTP

U3's six routes, and unlike U1 and U2 two of the context functions behind them changed shape.

**`Rooms.list_shift_rooms/1` selects from the other end of the order it displays**, and getting that wrong is silent. It was `Records.earliest_first/1` over every room the venue had ever had; a `limit` in front of *that* returns the venue's **oldest** rooms, satisfies every count assertion, and hides the shift the manager created a minute ago — which is the payoff of the flow the route exists for. It is now `Records.most_recent_rooms/2`: a descending scan with a `limit + 1` probe, re-ordered ascending in SQL around it, exactly `most_recent/2`'s shape for messages. The answer is a `Rooms.ShiftRoomPage` carrying `complete`, and the second arity takes `:recent` or `:all`.

**The ordering key is `starts_at`, not `inserted_at`, and they are different lists.** A manager who builds next month's rota before tonight's shift gets next month's rooms in the page. `starts_at` is chosen anyway because a page must be a *contiguous suffix* of the order it is displayed in — selecting on one column and displaying on another gives a scattered subset in which `complete` says nothing about *where* the rest is. **Assumption on the record:** a backdated shift at a venue with more than the bound's worth of later-starting rooms is reachable only through `extent=all`.

**`recent_shift_room_limit/0` is 30 and no relationship to `recent_message_limit/0`'s 50 is asserted anywhere** (issue #42). What the two do share is the rule: the number lives in the context and no caller may pass one. `HospitalityComsWeb.Extent` is where the word `recent`/`all` becomes one — it was `RoomController`'s private `extent/1` and moved when `EmployerController` became its second caller, which is `EntityId`'s precedent and keeps the refusal sentence in one place.

**A bound needs `limit + 2` rows to be observable, and `limit + 1` is what every fixture had.** Measured: the read selects `limit + 1` as its probe, so against a venue or a room holding exactly `limit + 1` the descending scan and an ascending one select the *same set*, and flipping the direction kills nothing. #48's four message fixtures and this unit's two shift-room ones are all at `limit + 2` now, where the flip kills three tests in each family. A count assertion was never the issue; the fixture size was.

**`Rooms.create_shift_room/3` and `Rosters.add_to_roster/3` hand back a row that can be rendered.** The room carries the `ShiftType` it was built from and the entry carries its `Engagement` — the structs already in hand inside the same transaction, not a `preload` re-reading a row a statement old. That is what lets one render function serve the create response and the list. `RoomController.rendered_shift_room/1` is public for the same reason `RoomChannel.rendered/1` is: an employer shape carrying `shift_type_id` where the person's carries `shift_type_name` would be one entity with two spellings.

**`Rosters.list_roster/2` preloads the engagement, and a client-side join could not replace it.** A `RosterEntry` carries no role label, so R13 had no source. Joining against the venue's people list has a hole that only shows in use: `add_to_roster/3` accepts an engagement whose term has **not opened**, while `list_engagements/1` answers only with engagements active at the instant — so next Monday's starter, on next Tuesday's rota today, renders as a bare UUID. **The test fixture must contain that starter or the hole is unobserved**, and both the context test and the route test assert the absence from the people list beside the label. `list_engagement_periods/3` is deliberately not preloaded: a different caller with a different association set gets a different function.

**R15's four refusals are one answer.** Another venue's shift room, another venue's engagement, an id naming nothing, and an engagement already on the roster — plus a malformed id — all `404` with one sentence, compared for **equality** in the test rather than matched separately. `Rosters` distinguishes `:already_rostered` internally and the transport is where that stops. The counter-argument is in `EmployerController`'s moduledoc rather than deleted: `:already_rostered` is reachable only after both ids resolved inside the caller's own venue, so it discloses nothing `GET …/roster` would not, and flattening costs the operator a usable message. Reversing it is a requirement change, not a bug fix.

**Removal answers `204` and the row stays** with `left_at` set (KTD6b); the test asserts the surviving row, because a route that deleted passes everything else. Two guards make that true and only one is this application's: `employer_role` holds no `DELETE` on `roster_entries`, so the grant tier refuses it before any code does.

**A missing id in a *body* is `400`; a present one that resolves to nothing is `404`.** `shift_type_id` and `engagement_id` arrive in bodies, so "you did not name the thing" and "the thing you named is not one you can use" are two different mistakes — `ClaimController`'s shape for a request carrying no `claim_code`. The tests assert the two bodies are **unequal**, which is the mirror of R15's equality.

**Two guards here are redundant and measured as such.** Widening `EmployerController`'s `@term_fields` to include `grace_period_minutes` and `venue_id` kills nothing: `ShiftRoom.changeset/3` casts two fields and `put_change`s the rest off the resolved shift type, so the controller's `Map.take/2` is a second line in front of a rule the changeset already holds. Removing `list_shift_rooms/2`'s `is_binary(grant_id)` guard kills nothing either, because `Venues.fetch_acting_grant/1` heads on the same guard. Both are kept — they protect different entry points — and neither should be read as covered by a route test.

**`Rosters.unrostered/3` is a friendly check, not the guard.** Deleting it kills exactly one test, the context's, and **not** AE8's route-level one: `roster_entries_no_overlap` refuses the second insert, the changeset arm maps to the same flat `404`, and the roster still holds one entry. The count in AE8's test is the requirement's literal words; the **status** is what a mutation moves.

## Five disclosures on the record

None is a bug and none is closed here. All are written down so a later unit decides about them deliberately.

**`engagements.person_id` is a globally stable UUID and `employer_role` can read it.** Two venues comparing ids out of band can therefore determine that the same human works at both — which is precisely the concurrency U9's disclosure default hides. It is inherent to the single-bridge design: the exclusion constraint keys on `(person_id, venue_id, period)`, so the person key has to be the same value at every venue. A per-venue pseudonym would need a second crossing or a per-venue mapping table, which is a KTD2 decision rather than an implementation one.

**#66 made that key readable to workers, and the step is on the record.** `room_messages.author_engagement_id` is venue-local by construction (KTD15b) and a rendered message now carries a globally stable *name* beside it — so a worker engaged at two venues, in both venue rooms, can tell from the messages alone that one human speaks in both. The capability already existed: `Rooms.list_venue_room_members/2` hands every member the `person_id` of every other, which is the disclosure directly above. What changed is that it no longer needs a join. It reaches **no employer** — `people` is person zone, `employer_role` holds nothing on it, `boundary_test.exs`'s sweep asks about column grants as well as table grants (measured: asking `has_table_privilege` alone fails 9 tests), and no employer-facing render carries the column. Closing it means a per-venue name, which is the KTD2-level change above rather than a rendering choice.

**#73 widened where that name appears and widened the disclosure by nothing**, which is worth stating rather than assuming. A conversation, a connection request and a peer message now carry the counterpart's name — but a conversation exists only because a request was accepted, a request only between two people who were visible to each other, and `list_visible_peers/1` has carried the name to exactly that audience since #66. The one case that looks new is a **connected** counterpart whose visibility lapsed: their name was disclosed while it had not, and a connection is permanent by design (R13). It reaches no employer, for the reason above, and `list_reachable_peers/1` — the audience picker's people half — is the same set plus nobody.

**#65 put a departed colleague's job title in front of people who never worked with them, and that is the whole of what it discloses.** A rendered message now carries the venue's own `role_label` for its author. To the venue's *current* people this is nothing new — `Rooms.list_venue_room_members/2` already hands out whole `Engagement` structs, label included, and `Peers.list_visible_peers/1` carries a counterpart's label by design. But that roll is the venue's **active** engagements and peer visibility lapses thirty days past a term's end, while a venue room keeps full history: so somebody who joined last week can read out of the history that a person who left two years ago was the head chef. It reaches **no employer** — the label is employer-authored, `employer_role` holds nothing on `room_messages`, and no employer surface renders a message. It is a job title at a venue, authored by that venue, attached to words that venue already retains indefinitely (KTD15c); closing it means either unattributed history or a snapshot label stored on `room_messages`, which is KTD2 broken for the reason a stored display name is.

**U9 acted on the half it could.** The employer-visible views expose no `person_id` at all: an employer names a worker by `viewer_engagement_id`, their own engagement at their own venue, and the entries that come back name venues. So no *new* surface hands the key out, and `boundary_test.exs` pins both views' column lists so one cannot be added quietly. The disclosure itself is not closed — `Engagements.list_engagements/1` still returns whole `Engagement` structs to an employer session, `person_id` among them — and closing it is the KTD2-level change above rather than a rendering choice.

**The HTTP surface renders a field list, so no client reaches the key.** `GET /api/employer/venues/:venue_id/engagements` is `{engagement_id, role_label, starts_at, ends_at}`, pinned in `employer_controller_test.exs` by an exact key set against a literal, with `Engagement.__schema__(:fields)` containing `:person_id` beside it as the control. The context function is unchanged; what is closed is the route, not the disclosure.

**`employer_role` holds table-level `SELECT` on `invitations`, and that includes `claim_code_digest`.** The digest is SHA-256 of 32 random bytes, so it is not a working credential and cannot be turned back into one — but `Records.outstanding_invitations/2` returns whole `Invitation` structs, so **a U6 endpoint that renders one wholesale ships the digest to the client.** Render a field list, not the struct. Narrowing the grant to named columns is the alternative and was not taken, because the digest is also what the claim looks the invitation up by. **U2 is the first route that renders an invitation, and it renders a field list**: `{invitation_id, role_label, starts_at, ends_at, code_expires_at}`, with the plaintext code beside it rather than inside it, and the same three pins the employer transport section describes plus a fourth — the returned code is hashed and compared against the stored digest, because otherwise "the response carries a plaintext code" and "the response carries a string" are the same green. **The disclosure is not closed**: `Engagements.list_invitations/1` still returns whole structs and no route renders *it*, which is the deferred "listing outstanding invitations" the origin names.

**U3's roster render is the third field list, and it is the one that could have leaked.** `GET …/roster` is `{engagement_id, role_label, joined_at}` rendered off a *preloaded* `Engagement`, so the struct carrying `person_id` is one field access away; the render is pinned by an exact key set with `Engagement.__schema__(:fields)` beside it. Adding `person_id` to it fails that test, measured.

**`Rooms.list_venue_room_members/2` hands every member of a room the `person_id` of every other member.** It returns whole `Engagement` structs and it is the only list in the tree that discloses one worker's identity key to another. U8/U9 render it: project a field list, and attribute on the engagement's `id` — the `author_engagement_id` a message already carries (KTD15b), venue-local by construction — rather than on `person_id`. The same shape as the `claim_code_digest` note above, aimed at a different consumer.

U8 acted on this half. `Peers.list_visible_peers/1` selects a field list rather than structs, and what it carries about a counterpart — their `person_id`, the shared venue, the employer-authored `role_label` — is exactly what the venue room's roll already discloses. **No email address**, which is the only other identifying column `people` has, and `peers_test.exs` asserts its absence with the positive test as the control. `Rooms.list_venue_room_members/2` itself is unchanged and still returns structs; U9 is where that lands.

**Peer visibility is employer-extensible by construction, and U9 widened what that reaches.** It derives entirely from `engagements`, and only an employer writes those. So a manager can issue an invitation whose term overlaps a former worker's engagement at that venue and manufacture co-rostering — hence visibility, hence the ability to send a connection request. Acceptance is still the addressee's, so no conversation results without consent.

U9 makes this reach one step further than it did, and the step is on the record rather than hidden: manufactured co-rostering now also opens the *profile*, because `Profiles.fetch_peer_profile/2` gates on visible-or-connected. What it opens is bounded — the manufacturing venue's own concurrency rule follows whoever it is manufactured for, so the peer sees what that venue sees plus declared entries the worker published — and the remedy is per-peer and immediate: one `set_disclosure/4` row takes an entry away from that person and from nobody else. It is not closed here because closing it means either a peer default of hidden, which makes the surface useless at the moment it is first seen, or gating the profile on a *connection* alone, which is a product decision about what "peer" means rather than an implementation one.

**`VisibleEntry.entry_engagement_id` is stable across readers, exactly as `person_id` is.** An earlier moduledoc called it "venue-local by construction", which is false in the only case the disclosure rule exists for: two venues reading the same worker's third-venue entry get the same `entry_engagement_id` and the same `attested_entry_id` and can join on either out of band. Neither is resolvable through either venue's own session. Subsumed by the `person_id` disclosure above rather than additional to it, and written down so the claim is not read as more than it is.

**A channel derives its session per join, not per event.** So a token deleted while a channel is open leaves that channel able to send until it next joins, unless `PersonAuth.disconnect_sessions/1` reached it — which log-out, magic-link redemption and email change all do. The reasoning for per-join, and what it does and does not cost, is in `HospitalityComsWeb.ChannelAuth`'s moduledoc.

**U10's erasure was the case to watch, and it is decided rather than inherited.** `Lifecycle.erase_person/1` returns the token rows it deleted, exactly as `Accounts.delete_person_session_token/1` does, so whichever surface exposes erasure disconnects the transports the way log-out already does; the context does not call `PersonAuth`, because no context calls the web layer. **The teardown is not what makes the channel powerless.** Erasure ends every engagement and disconnects every conversation in the same transaction, and authorization is per event, so a channel that outlived the broadcast sends its next frame and is refused on the same process with nothing having rejoined. `revocation_test.exs` asserts both halves — the refused send and the refused rejoin at *every* venue at once, the second venue being the control that distinguishes erasure from ending one engagement.

## Demo

`HospitalityComs.Demo` and `HospitalityComsWeb.DemoController`, both in `dev_support/`, reached over HTTP at `/api/demo/*` behind `Application.compile_env(:hospitality_coms, :demo_routes)` — set in `config/dev.exs` and `config/test.exs` and nowhere else. `priv/repo/seeds.exs` calls `Demo.seed/0` and refuses under `:test` and `:prod`.

**The issue put these in `lib/` and that is not survivable.** `lib/` compiles in `:prod` and `Clock.Offset` does not, so a demo module there either fails `MIX_ENV=prod mix compile` or reaches the override through `apply/3` and ships a control that ends engagements across every employer. KTD5b's absence is structural or it is nothing. `demo_test.exs` asserts it three ways — `MixProject.elixirc_paths(:prod)`, every `dev_support/` module's compiled source against those paths, and **no module compiled from `lib/` calling one compiled from `dev_support/`**, read out of the `imports` chunk. That last check cannot see a compile-time struct expansion or a typespec, which is why CI now also runs `MIX_ENV=prod mix compile --warnings-as-errors`. Neither substitutes for the other.

**`run_due_work/0` drives the workers directly and never the queue.** Oban's staging query is bound to real wall-clock time, so a control that advanced the clock and waited would demonstrate nothing. It calls `ExpireEngagement.perform/1` and `RetentionSweeper.perform/1` on jobs built from the workers' own changesets and applied rather than inserted — **with a JSON round trip on the args**, because `oban_jobs.args` is `jsonb` and the worker matches string keys; an applied changeset still carries the atom-keyed map and the worker refuses it by function clause. It deliberately does **not** call `EngagementSweeper.perform/1`, whose only contribution is the insert, and it uses an **unbounded lower edge** where that sweeper uses a day: a clock that jumps thirty-one days puts every closed term outside a window built for a queue that ticks every five minutes, and since U10 the announcement is what stamps `retained_message_copies.delete_after`. `demo_test.exs` pins the production window separately so the two cannot drift silently. Two consequences of that edge are now written beside it: **the demo deletes archives the production path provably would not** (a term outside production's window keeps a null deadline for ever; here it is announced, stamped and swept in one action), and `epoch()` with a batch bound and `desc: ends_at` is the non-converging combination `list_expired/3`'s own moduledoc names — unreachable at manifest scale.

**`:dev` sets `testing: :manual` too, and that is a fix rather than symmetry with `:test`.** Oban's cron stages at the *real* instant while `RetentionSweeper.perform/1` reads the *injected* clock, so with queues running in `:dev` a single `POST /api/demo/clock {"advance": {"day": 31}}` deleted a month of retained messages within the hour, unattended, and `EngagementSweeper` stamped archive deadlines within five minutes. The wall-clock argument above covers the *claim-scheduled* `ExpireEngagement` job, which genuinely waits; it does not cover cron. `demo_test.exs:213`'s "a clock advance alone deletes nothing" was true only because `config/test.exs` set the key — an environment-conditional assertion with nothing recording that. `demo_test.exs` now reads both config files through `Config.Reader`, with the merged cron plugin and non-empty queue list as the control.

**The control holds no authority and borrows one venue's at a time.** `end_all_engagements/1` takes a person id and no scope; it enumerates across venues through `Repo` — what `EmployerRepo` refuses — and closes each engagement under an `EmployerScope` built from a live grant at *that* venue, so R22's refusal is `end_engagement/2`'s own rather than a second copy of KTD17. The decision is made *before* the first close, so `Engagements.would_orphan_venue?/2` is public now: the same question `end_engagement/2` asks, asked by the function that asks it. **It is not the enforcement** — no lock, so the close re-decides under `FOR UPDATE` and refuses regardless. It opens with `Venues.fetch_acting_grant/1` like `end_engagement/2` and `renew_engagement/3` do, which it did not: it was the one employer-scoped entry point in `Engagements` where a session holding a revoked grant got a real answer. A dead scope now answers `false`, which is what every other unanswerable case answers.

**Which is why "all-or-nothing" is now a property of the ordinary case rather than a claim.** Each close is its own transaction and the pre-flight takes no lock, so a refusal from inside the loop leaves the closes before it committed. `end_all_engagements/1` answers `{:error, reason, closed}` and the controller renders `ended` beside the envelope; `:not_found`, `:last_grant_holder` and `:no_grant` all carry `[]` by construction. `end_engagement/2`'s own `:not_found` is translated to `:stale` inside the loop, so the control's `:not_found` means "no such person" and nothing else — a 404 about a person who plainly exists was the alternative.

**The target set is what the person holds, not what has not closed.** `Engagements.list_person_engagements/1`. `end_engagement/2`'s set is one state wider on purpose (a mistaken claim can be taken back, producing the empty range); applied to *every* engagement a person holds under a backwards clock it collapsed terms to their own opening instead of ending employment — and **that permanently wedged `run_due_work/0`**. Measured: wind the clock back past Mira's founding term, end her engagements, wind forward three days, and the archive deadline `ends_at + 90 days` lands before words she had already spoken; `retained_message_copies_deadline_after_sending` refuses the row, Postgres evaluates a CHECK on the candidate *before* `ON CONFLICT` arbitration so `on_conflict: :nothing` does not save it, and the unbounded lower edge re-reached the poisoned term on every later run whatever the clock said. The fix is in the demo and not in `Lifecycle`: production cannot reach the state, because `scope.now` is monotonic at the HTTP boundary. **Residue on the record:** a clock wound back more than ninety days *inside* a term whose messages lie beyond that window still produces the refusal; nothing in the manifest reaches it, and `mix ecto.reset` is the remedy.

**The seeds build scopes at historical instants and never move the clock.** Every context stamps from `scope.now`, so a past roster is written by handing the call a scope at the instant it happened. Getting that wrong is not a compile error and does not look like a failure: the roster period simply misses the shift and the room comes back empty. Every instant is relative to `Clock.now/0` at seed time, so a database seeded at 15:40 has a shift live at 15:40.

**Ana's Harbour term opens before the venue she manages, and that ordering is load-bearing.** `end_all_engagements/1` walks a person's engagements oldest first; founded the other way round it would refuse on its first step and a control with no pre-flight at all would look correct.

**Seeding is all-or-nothing over nine anchors, not six.** Two venues by name, four people by address, and the three curated rows — declared entry, correction request, disclosure — that `write/1` writes in its last phases. All six of the originals exist by phase four of eleven, so a run interrupted after them answered `:present` and wrote nothing, with the profile surface silently short a row. All present writes nothing; none present seeds; anything between is `{:error, :partial_manifest}` and `mix ecto.reset`. Demo rows carry `Demo.venue_pattern/0` (`"% (demo)"`) and `Demo.person_pattern/0` (`"%@demo.invalid"`), which `EngagementsFixtures.purge/0` reads — so an aborted `demo_test.exs` is ordinary fixture residue rather than the guard's loud "written by nothing in this tree" category.

**Every id the manifest carries names a row the demo cannot destroy, and that is a constraint on what may be added.** `connection_id` was "the only connection Tomo is a party to" and `pending_request_id` was `List.first/1` of his inbox — so accepting the seeded approach raised `Ecto.MultipleResultsError` and declining it raised `MatchError`, out of a function spec'd `{:ok, manifest()} | {:error, :partial_manifest}`, permanent for that database, from the first thing a demo client does. Both are keyed on the seeded *pair* now, oldest first.

**`/api/demo/*` requires the header `x-demo-control` on every state-changing action.** Unauthenticated and same-origin-reachable are different properties: a CORS-simple `fetch(…, {mode: "no-cors"})` from any page a developer has open reaches this surface with no preflight, and `Plug.MethodOverride` extends that to `DELETE /api/demo/clock`. A custom header is not simple, so requiring one forces a preflight this application answers with no CORS headers. Reads are left open. **`unit_pair/1`'s `is_integer(count)` was already blocking the clock by accident** — urlencoded bodies yield strings and JSON is not a simple content type — which is now written down, because relaxing it to accept `"31"` would give that back.

**Two more test files are not sandboxed:** `demo_test.exs` and `demo_controller_test.exs`, for U5's reason plus the global clock.

**Three refusals in this surface are deliberately unreached and `demo_controller_test.exs` says so:** `:stale` and a changeset, which need a real interleaving and are the only two that can carry a non-empty `ended` list; and `Demo.permitted/1`'s `:no_grant`, which wants a venue holding an active engagement and no live grant at one instant, and `Venues` refuses to revoke a venue's last live grant.

**`.formatter.exs` did not cover `dev_support/` until this batch.** CI's `mix format --check-formatted` reads that list, so ~1250 lines of U11 plus `clock/offset.ex` and the Credo checks sat in a blind spot the check could never fail on. `inputs` is `{config,dev_support,lib,test}/**` now.

## Authentication

Magic link in, bearer token out. `POST /api/log-in` registers the address if it is new and mails a link; `POST /api/log-in/token` redeems it and returns the API token; `GET /api/me`, `PATCH /api/me` and `DELETE /api/log-out` require it, as do the four person-side room reads under **Rooms and rosters** above.

**`GET /api/me` is `HospitalityComsWeb.PersonController`'s, not `SessionController`'s** (#66). That module is about the session — asking for a link, redeeming it, ending it — and `/api/me` answers with a *person*; once there was a write on the same resource, leaving the read behind would have put one resource under two controllers on one path. `PersonController.rendered/1` is public and `SessionController` calls it for the person in the redemption reply, which is `RoomChannel.rendered/1`'s precedent. `session_controller_test.exs` compares the two bodies field for field, so a second spelling fails rather than drifts. There is no password anywhere in the tree and no cookie session — the generator's password column, changeset, and `bcrypt_elixir` were removed, because with no HTML layer nothing could ever set one.

The API token *is* the generated session token: a row in `people_tokens`, base64url on the wire and SHA-256 in the column. Every context stores a digest, session included — the column is the bearer credential for this API, so a `SELECT` leak must not yield a working one. Deleting the row ends the session on the next request **and on the next channel join**, because a socket keeps the token's digest and `ChannelAuth.join_scope/1` looks it up again against the same row and the same horizon. `disconnect_sessions/1`'s broadcast drops the transports promptly; it is not what makes them powerless.

Every error the API returns is one envelope, built only by `HospitalityComsWeb.ErrorEnvelope`: `{"error": {"code": <status atom>, "message": ..., "fields": {...}}}`, with `fields` present only for per-field validation failures. Controllers, `PersonAuth`, `ErrorJSON` and every channel refusal go through it; do not hand-roll a body. `ErrorEnvelope.for_changeset/3` is the one place Ecto's `%{count}` placeholders are interpolated.

Production requires `MAGIC_LINK_BASE_URL` — `config/runtime.exs` raises without it, because the `localhost:4000` default in `config/config.exs` fails silently by mailing links to the wrong host.

**`POST /api/log-in` is rate limited per caller and nothing else on the router is.** `HospitalityComsWeb.LoginRateLimit` is one ETS table, a fixed window, and no dependency — ten attempts per remote address per fifteen minutes, `429` in the standard envelope with a `retry-after`. It is a pipeline of its own rather than a line in `:api`, because that route is the only one an anonymous caller can use to write a row and send an email; redemption needs a link and everything else needs a session.

**The key is `conn.remote_ip` and it must never become the address in the body.** The merged log-in door answers identically for a known and an unknown address, and a per-address throttle — "one link per address per fifteen minutes" — would answer `429` for one and `202` for the other, which is a *better* enumeration oracle than the merge closed: no timing analysis and no mailbox, just a status code. A future duplicate-suppression suppresses the **email** and leaves the **response** alone. `login_rate_limit_test.exs` asserts identical answers on both sides of the limit, because the comparison at the limit alone is satisfied by a limiter that refuses everybody.

The plug runs after `:fetch_person_scope` and takes its instant off the scope, so it reads no clock and is **not** a `:boundary_modules` entry. The row is `{ip, window, count}` keyed on the address, not on the pair — so a stale bucket is *reset in place* by the next request rather than accumulating beside a new one, which is what lets `prune/0` reclaim on a plain interval without agreeing with any clock. `conn.remote_ip` is the peer address: behind a load balancer the limit is global, and `x-forwarded-for` is deliberately not consulted because an unauthenticated caller sets it freely and trusting it would let anybody mint a bucket per request.

**`ConnCase` gives every test its own `remote_ip`, and that is the suite's whole isolation from the counter.** ETS is node-local and nothing resets the table, so the key space is what partitions the tests. It is load-bearing today rather than defensively: `session_controller_test.exs` makes ten `POST /api/log-in` calls at one pinned instant, and both mutations of the partition turn that file red.

**`Lifecycle.reap/1` and `Workers.AccountReaper`** are issue #15's other half, hourly on the `:lifecycle` queue at `30 * * * *`. Nothing removed a `people_tokens` row past its horizon except consumption, and nothing removed an unconfirmed `people` row at all.

The deleting code is in `Lifecycle` because KTD21 says so and because the near alternative is worse: `Accounts` is already the one enumerated exemption, and its bound is a test that counts every base table across a log-out and asserts `people_tokens` is the only one that moved — which reaping `people` can never satisfy. It is a **second entry point rather than two more triggers on `sweep/1`**: those four read `delete_after` columns stamped once by an event from a value that can no longer move, and these two *compute* from `inserted_at`, so a six-item list would be a list a future author copies the wrong half of.

**The token predicate is the exact complement of the authenticator's**, not a second copy of three numbers. Each `verify_*_query` admits a token when `inserted_at > instant - validity`, strictly, so a token whose validity elapses exactly at the instant asked about is already refused — and the reap is `<=` where `sweep/1` is `<`. The two boundaries differ by one instant and each matches the rule that governs it. A fourth, catch-all disjunct reaps an unrecognised context at the longest horizon, because three contexts enumerated is a hole the day a fourth is written and the hole is silent.

Unconfirmed people go at **thirty days**, `<` like every other deadline, and the number is chosen against a constraint: it must exceed every token validity, because `people_tokens.person_id` is the only foreign key into `people` that is not `ON DELETE RESTRICT`. Every other one is, and **an unconfirmed person can hold none of those rows** — `confirmed_at` is set by the only path that mints a session token, and every context that writes them takes a `PersonScope` carrying a real person. If a later unit breaks that the delete raises `foreign_key_violation` and the job fails loudly, which is why the predicate carries no `NOT EXISTS` list: five tables is a list somebody gets wrong later, silently.

**Sweeping frees the address.** The row is gone rather than pseudonymised and `people_email_index` is partial on `erased_at IS NULL`, so an unconfirmed address becomes re-registerable exactly as if it had never been used. That is the accepted trade — an address sent a link and never redeemed for a month is not in use, and keeping the row for ever hands an anonymous caller a permanent way to burn other people's addresses.

**Neither reap statement has a lower bound and that is the opposite of `Engagements.list_expired/3`.** That sweep needs a floor because it does not consume its rows; both of these delete what they select, so they advance by construction, and a floor would leave a backlog nothing ever reaches. No `retention_runs` row is written: that record exists because retention destroys the only copy of a person's words, and this destroys a credential the authenticator had already stopped honouring plus a row its owner recovers by registering again. The counts are returned and the worker logs them.

`lifecycle_reap_test.exs` is **sandboxed** and `async: false`, and the second half is the reason: `reap/1` is scoped to no person and no venue, so it reaches every `people` and `people_tokens` row in the database and must not run beside a file that has committed some. ExUnit finishes every async module before starting a synchronous one.

`people` is already shaped for U10 erasure: `email` is nullable, its unique index is partial on `WHERE erased_at IS NULL`, and two check constraints hold `erased_at` and `email` in opposition. Erasure nulls the address; nothing else may.

## Display names

`people.display_name`, from `*_add_display_names.exs` (#66) — the second column this schema holds about a human and the first readable one. It is **given** at registration from `HospitalityComs.Accounts.DisplayName`'s sixty-four public-domain literary characters, and `Accounts.update_display_name/2` is how it changes. `Accounts.register_person/2` is the one door a person row comes through, so putting the generator on `Person.registration_changeset/4` makes "every person has a name" a property rather than something five fixtures and `Demo.seed/0` each have to remember.

**Five surfaces read it now.** #66 put it on the venue-room message and the peer list; #73 put it on the conversation, both connection-request shapes and the peer message. Every one of the five reads it through a join and none stores a copy, so a rename reaches all of them and erasure reaches all of them in one statement — which is the property the column exists with rather than a coincidence of five call sites agreeing.

**Collisions are allowed, and the argument is a privacy one rather than a cost one.** `CLAUDE.md` already records `engagements.person_id` as a globally stable key two venues could compare out of band; a globally *unique* readable name would be a second such key, in plain text, readable by every worker rather than only by somebody holding a database connection. Collisions are the only thing that stops "Captain Nemo" being as good as a person id. So the engagement id stays beside the name wherever attribution matters, and the client renders `Captain Nemo · 4a3f1b2c`.

**Erasure overwrites it** with `Lifecycle.erased_display_name/0` (`"Former colleague"`), in the statement that nulls the address. It is a **separate constant** from `erased_label/0`'s `"Former team member"` and no relation is asserted between them: one is what an employer wrote about a job and the other is what a person called themselves.

**There is deliberately no check constraint pairing it with `erased_at`.** The `email` pair exists to keep a partial unique index coherent and this column has neither a unique index nor a presence/absence rule — it is replaced, not removed; `engagements.role_label` is the tree's existing case of erasure overwriting text with a constant and it carries no CHECK either; and a CHECK here would have to pin a *UI string* in a migration, which is #42's defect class. The CHECK was available at the cost of one `constant_agreement_test.exs` row and is recorded as declined. What the column *does* carry is `people_display_name_present` and `people_display_name_within_bound`, for a different reason: the erasure write is an `update_all` and meets no changeset, which is `retained_message_copies`' situation reached from another direction. `Person.display_name_changeset/3`'s `validate_length` and its `check_constraint` declaration are a **redundant pair, measured** — either alone kills 0, both together kill 2, and dropping the database CHECKs kills 5.

**The guard is `lifecycle_test.exs`'s whole-row comparison**, which fails on any column the erasure statement forgets. It grew two controls when the name arrived: the person is renamed to a known string first, because a field that already holds the target value is invisible to a diff, and `accounts_test.exs` asserts the erased constant is not in the generator's list, because otherwise one registration in sixty-four would make that diff vacuous at random.

`display_name` is **not** in `config :phoenix, :filter_parameters`. That list is an allowlist since #53, so it prints as `[FILTERED]` by default, and `AGENTS.md`'s avoid-list names `first_name`/`last_name`/`full_name`. Adding it would be the bug.

`person_controller_test.exs` is the **first controller test in the tree that may be sandboxed**, and is: nothing on that surface reaches an employer, so there is one connection and no cross-repo invisibility to work around.

**Every `Accounts` function that reaches a repo takes a `PersonScope` first** (#18), so an employer caller is refused by function clause rather than by a check somebody has to remember. U3 built that mechanism and for eight units it protected `sudo_mode?/2` alone, which reads nothing — everything else took a bare address, a bare token or a bare `DateTime`, so `employer_scope.now` reached the whole context. `session_token_digest/1` is the single exception and it is enumerated rather than incidental: it is `:crypto.hash/2` of its argument and reaches no repo, no row, no clock. `person_zone_test.exs` sweeps `Accounts.__info__(:functions)` rather than a list, so a seventeenth function is covered the day it is written, and pins that exception as a literal inside the assertion.

**Two head shapes, and the split is per function rather than a style.** Where the scope's person *is* the subject the head destructures it and there is no person argument — `sudo_mode?/2`, `generate_person_session_token/1`, `update_person_email/2`, `deliver_login_instructions/2`, `deliver_person_update_email_instructions/3`. Everywhere else the subject is a credential, an address or an id handed in, the head is bare `%PersonScope{}`, and the scope's person is deliberately not read. **The anonymous form is what makes the second shape possible**: a scope answers which zone and when before it answers who, and `get_person_by_session_token/2` is the call that *produces* the person a scope will carry, so an authenticated one would be circular. `PersonAuth.fetch_person_scope/2` builds an anonymous scope from the request's instant, authenticates with it, and builds the real scope from the answer; `ChannelAuth.resolve/1` and `join_scope/1` do the same and neither adds a clock read. Requiring `person: nil` on the second shape was rejected — `delete_person_session_token/2` is called from an authenticated request about its own credential.

**One clause per function, and no guard macro.** A second clause "refusing everything else" is the runtime check U3 replaced; a `defguard` would expand to `is_struct(scope, PersonScope)`, which cannot destructure and so is weaker than the head. The forty-odd `%PersonScope{...}` heads in `Peers`, `Profiles`, `Rooms`, `Engagements` and `Lifecycle` are the precedent.

**None of it is the boundary and `boundary_test.exs` keeps saying so.** `Accounts` goes through `Repo`, which holds every privilege, so an employer caller who *forges* a `PersonScope` from their own instant still reads `people` — asserted, so the claim cannot quietly grow into a stronger one. What closes the zone is the grant on `EmployerRepo`'s role plus U3's `REVOKE`; what the shape closes is reaching the zone by accident.

`deliver_person_update_email_instructions/3` now takes the **new** address and derives the rest from the scope, where it took a `Person` doctored to carry the new address plus the old address beside it. The freedom removed was unusable: `update_person_email/2` verifies against `"change:#{person.email}"`, so any other value minted a token nothing could redeem.
